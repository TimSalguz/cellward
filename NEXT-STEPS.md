## Неподвижные правила

- Выбранная сеть относится к **фактически выполняющему запрос процессу**.
  Одинаковое имя программы не означает общий сетевой контекст. Передача
  запроса уже работающему процессу — отдельный случай, его сеть не меняется
  от нового выбора в пикере.
- Не составлять список «браузеров», «терминалов» и исключений по имени как
  основу политики. Учитывать идентичность экземпляра, процесса, контейнера и
  его профиля данных; несовершенное распознавание сообщать честно.
- Любой сбой звена, DNS, смены сети или политики маршрута закрывает выход, а
  не переводит программу на сеть хоста. Ни на миг не держать два выхода
  одного экземпляра. Ни одна диагностическая проба не поднимает запрещённый
  прямой VPN-маршрут.
- Одна запущенная программа не получает две сети одновременно. Смена сети
  контейнера меняет её для **всех** его процессов и разрывает соединения;
  одновременная работа в разных сетях требует отдельных экземпляров. Общий
  writable-профиль между ними по умолчанию не использовать.
- Прямой входящий трафик, мосты между контейнерами, split routing и доступ к
  локальной сети — только явные ограниченные разрешения. Отсутствие настройки
  означает отказ.

- [ ] На схеме показывать интерфейсы и возвращения между namespace,
  последовательность всех звеньев, отдельный боковой LAN-маршрут, DNS
  endpoint и DNS программы. Для каждого hop — кто знает его адрес, кто
  видит следующий hop и конечный пункт, где раскрывается содержимое,
  измеренный RTT и оценку добавленной задержки. Не выдавать оценку за
  гарантированный пинг.
- [ ] В дальнейшем — импорты форматов/ссылок, OpenVPN и userspace-протоколы
  (sing-box или обоснованная альтернатива), единый контракт нового backend;
  отдельная «зона со своим клиентом» только с предупреждением о доверии
  вендорскому бинарю. «Умная» split-зона — отдельный явно негерметичный тип,
  не настройка по умолчанию обычной зоны.

## P3 — безопасность, диагностика и входящие соединения

- [ ] Разобрать частые запросы «неизвестная программа» на реальных запусках:
  измерять, на каком этапе теряется владелец сокета (таблица `/proc/net`,
  дескрипторы процесса, `sock_diag`/cgroup, запись запуска), без вывода
  секретов или подмены догадкой. Проверить короткоживущие процессы и
  Chromium-подобные браузеры в VM. Не объединять разные неопознанные
  соединения в одно разрешение.

- [ ] Расширить `doctor` проверками **снаружи**: DNS, IPv6, egress-IP,
  WebRTC, endpoint DNS и возможная подмена ответа. Для каждого канала
  [модели утечек](docs/LEAK-MODEL.md) — тест с «злым хостом», а не только
  осмотр правил внутри зоны.
- [ ] Прогонять матрицу fail-closed: потеря любого hop, смерть DNS/прокси,
  выключение/возврат сети хоста, реконнект, смена маршрута и LAN, отказ
  nftables/брокера, сон/пробуждение. Отмечать и тестировать поведение
  каждого сбоя; не добавлять тихий direct fallback.
- [ ] Закрывать обнаруженные обходы через порталы, D-Bus, доступные Unix-
  сокеты, общий `/tmp`, файлы дома, X11, наследованные дескрипторы и
  службы хоста. Права контейнера и сетевые правила могут только сужать
  возможности зоны. Проверять открытые каналы из `ROADMAP.md` и
  `docs/LEAK-MODEL.md` по мере каждого релиза.
- [ ] Закрепить диагностику PipeWire/WirePlumber и автоматический VM-тест
  звука в Chromium-подобном браузере и Firefox: звук через разрешённый
  путь, микрофон по отдельному разрешению, никакого открытия сырого
  PipeWire ради исправления звука.
- [ ] Явный **port forwarding внутрь зоны** исследовать как отдельное
  необязательное разрешение службы (адрес/порт/протокол/источник/срок).
  По умолчанию входящие остаются закрыты. До реализации нужны модель угроз,
  UI «кто сможет подключиться» и VM-тест отказа для всех остальных портов.
- [ ] Сетевой монитор/фаервол по контейнерам и программам: учёт потоков,
  локальный журнал, правила на домены/IP/протоколы и запрос разрешения при
  соединении. Не обходить уровень запретов зоны; лимиты и сроки хранения
  задать явно.
- [ ] Отдельный параноидальный режим `ask-every-destination` (не включать
  вместо нынешнего запроса «можно ли программе сеть вообще»): правило
  привязывать к контейнеру и программе, затем к точному FQDN, домену с
  поддоменами, IP или CIDR, порту/протоколу и сроку (одно соединение,
  текущий запуск, постоянно). Явно показывать, что разрешение для `*.example`
  шире, чем для `www.example`, а разрешение по IP может открыть другие сайты
  на том же CDN. Проверить приоритет deny, отзыв правила, IPv6, QUIC и UDP,
  смену DNS-ответов, CNAME и утрату DNS-имени. Вариант «домен целиком»
  рассчитывать по Public Suffix List, а не отрезанием слова перед точкой:
  `co.uk` или публичный суффикс не должен становиться разрешённым wildcard.
- [ ] Для строгого доменного решения не считать наблюдённое DNS-имя
  доказательством назначения соединения: при DoH/DoT, ECH, общем IP/CDN или
  прямом IP оно может быть неизвестно либо относиться к другому сайту.
  Выбрать проверяемый способ привязки имени (контролируемый резолвер и
  приложение/прокси с явным именем) или отказывать с предложением
  IP-правила; никакого тихого разрешения всех адресов по догадке.

## P4 — остальной продукт и выпуск

- [ ] Довести интерфейс контейнеров/прав: объяснение источника каждого
  разрешения, запросы в момент обращения, безопасные пресеты, перенос
  программы с данными в отдельный контейнер, понятные сообщения об отказе.
- [ ] Расширять изоляцию по умолчанию с миграцией пользовательских ярлыков и
  обработчиков ссылок, проверкой путей в аргументах запуска и отсутствием
  обхода пикера. Права `OpenFile`/`OpenDirectory` — через документный портал,
  не запуском программы хоста без вопроса.
- [ ] Системные зоны, службы и интерфейсы хоста — единый контракт с
  пользовательскими маршрутами; защитить применение Nix-конфигурации от
  случайного автозапуска запрещённого узла.
- [ ] i18n, клавиатурная доступность окон, тесты GNOME/KDE/niri, ясные
  предупреждения о потере несохранённого и разрыве соединений.
- [ ] Автоматизировать CI (`nix flake check`, shellcheck, unit/VM/leak-тесты),
  релизы и пакетирование для nixpkgs; перед выпуском сверить обещания README
  с реально проверенными гарантиями. Подробные хвосты M2–M10 остаются в
  [ROADMAP.md](ROADMAP.md), этот файл задаёт порядок по риску и зависимостям.

## Порядок ближайших изменений

Параллельная работа над интерфейсом, языками и темами приложений описана в
[`docs/UI-PLAN.md`](docs/UI-PLAN.md). Выбор палитры окна — первый завершённый
шаг; английский язык как основной и настройка темы контейнерных приложений
ещё требуют реализации и проверок безопасности.

1. Зелёный полный VM-прогон и точные проверки UDP при живой смене.
2. Привести ⇄, меню и рамку к фактическому состоянию контейнера; убрать
   название «перезапустить» там, где меняется сеть на ходу.
3. Запуск в двух сетях через явные отдельные экземпляры и наблюдение
   фактического процесса, без классификации приложений по имени.
4. Единая публикация маршрутов и жизненный цикл звеньев.
5. DNS предыдущего hop, прокси-звенья, локальные боковые маршруты и
   расширенная схема; затем оставшиеся бэкенды и продуктовые этапы.
