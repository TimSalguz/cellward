# Маршруты, локальные сети и приватность цепочек

Черновик следующего этапа после первой цепочки `inner --via outer`. Его главное
правило: конфигурация подключения и разрешённый путь — не одно и то же.

## Пул узлов и разрешённые маршруты

В пуле могут лежать `home`, `nl`, `ch` и другие VPN/proxy-узлы, но программы
видят только явно опубликованные маршруты, например:

```text
home
nl
nl → ch
```

При таком наборе `ch` — внутренний узел: его нельзя поднять напрямую, выбрать в
пикере или автоматически запустить при загрузке. Конфигурация системы, Stillconf
и диагностические пробы не должны превращать наличие узла в разрешение маршрута.
Проверка графа выполняется до запуска первого звена; частично разрешённый путь
не запускается.

Для нового общего пула сначала включается строгая публикация. Узел хранится
один раз в `.nodes/<имя>/config.conf`; маршрут в каталоге зоны содержит только
ссылку `[Node] Name` и, при необходимости, `[Chain] Via`:

```sh
cellward routes enable
cellward node add ch ./ch.conf
cellward route add ch-via-nl ch --via nl
cellward routes allow ch-via-nl
cellward node add vps ./vps.conf
cellward route add vps-via-ch vps --via-user ch-via-nl
cellward routes allow vps-via-ch
```

Получаются разрешённые маршруты `nl > ch-via-nl` и
`nl > ch-via-nl >> vps-via-ch`, но не прямые `ch` и `vps`. Один знак `>`
означает выход через системный VPN, два `>>` — через пользовательскую
VPN-зону; поэтому смена типа внешнего звена не наследует старое разрешение.
Допустима и большая
глубина: `--via-user` ссылается на предыдущий пользовательский маршрут, чей
собственный туннель уже выходит через предыдущие звенья. Перед запуском
проверяются все пользовательские префиксы, наличие VPN в каждом из них и
отсутствие циклов. Внешние звенья поднимаются по порядку. Потеря внешней зоны
обрывает внутреннюю, не переводя её транспорт на сеть хоста. Внешняя зона с
`connection = ask|manual` не поднимается косвенно: её нужно включить явно до
запуска внутренней.
`cellward route add ch-direct ch` создаст отдельную *неопубликованную* зону;
Cellward не позволит опубликовать одновременно прямой и цепочной путь к одному
узлу. Секрет не копируется в конфиги маршрутов, а при запуске читается из пула.
Отсутствующий или повреждённый узел приводит к отказу, без перехода на сеть
хоста. Существующие зоны с полным `config.conf`, включая созданные командой
`cellward add inner inner.conf --via outer`, работают как прежде. Внешний hop
цепочки может быть системной зоной (`--via`) или уже созданным пользовательским
маршрутом (`--via-user`). IPv6-транспорт внутреннего туннеля доступен, только
если предыдущее звено имеет глобальный IPv6-адрес и маршрут по умолчанию через
свой VPN-интерфейс. Иначе промежуточный uplink остаётся IPv4-only; внутренний
сервер с IPv6-адресом вызовет отказ вместо бессмысленного ожидания рукопожатия.
Такой маршрут требует работающего системного брокера для соединения
двух пользовательских пространств имён. Для цепочки только из пользовательских
VPN достаточно включить `services.cellward.system.enable = true` и добавить
своё имя в `services.cellward.system.users`; системные VPN-зоны для этого не
обязательны. Без брокера запуск откажет, прямого обхода не будет.

Первый слой публикации маршрутов доступен через `cellward routes enable`. Команда
включает строгий, изначально пустой список в `.routes` каталога состояния:
конфиги зон остаются на диске, но не появляются в пикере и не запускаются, пока
не выполнено `cellward routes allow <зона>`. Для зоны с `[Chain] Via = nl` в
список записывается точный маршрут `nl > ch`; смена `Via` не наследует старое
разрешение. Для зоны, которая только заимствует системный туннель, запись
имеет вид `nl => apps` и также закрепляет выбранный системный hop.
`cellward routes list` показывает опубликованное, `routes deny`
убирает маршрут. После включения удалённый или повреждённый `.routes` тоже
означает отказ, а не возврат к открытому старому режиму. Изменять публикацию работающей зоны команда отказывается:
сначала её нужно опустить. При ошибке чтения или синтаксиса `.routes` новые
запуски отказывают, а не игнорируют политику. Отсутствие `.routes` сохраняет
поведение старых установок, чтобы обновление не отключило их молча.

Для системных узлов NixOS есть отдельный опцион
`services.cellward.system.directRoutes = [ "nl" "home" ];`. `null` оставляет
старое поведение, пустой список запрещает все прямые системные маршруты. При
строгом списке `autoStart = true` у неопубликованной системной зоны — ошибка
конфигурации, а её `system-zone up` отказывает и при ручном запуске или пробе.
Неопубликованный системный узел можно хранить с `autoStart = false`, но он пока
не может быть внутренним звеном пользовательской цепочки: в текущей реализации
внутреннее звено — пользовательская зона, и одинаковый ключ в обоих уровнях
по-прежнему запрещён. При применении строгого списка уже *работающие* системные
зоны вне него останавливаются: их программы теряют сеть, но остаются в своём
пространстве с одним `lo`. Это намеренная остановка старых прямых рукопожатий,
которую обычное обновление зон иначе не делает. После перезагрузки эти зоны
тоже не запустятся.

Пул позволяет переиспользовать один пользовательский VPN-конфиг в разных
маршрутах без копирования. Маршрут теперь может иметь несколько пользовательских
звеньев, но звено пока должно быть туннелем WireGuard/AmneziaWG или OpenConnect,
а не proxy-транспортом или боковым LAN-выходом.
Включённая политика допускает хранить неопубликованную прямую зону с тем же
VPN как конфиг узла, но откажет опубликовать её рядом с цепочной. При выключенной
политике старый строгий запрет таких копий остаётся. Список пользователя и
системный `directRoutes` независимы: разрешение `nl > ch` не публикует прямой
системный `ch`.

При добавлении и каждом подъёме цепочки Cellward проверяет, что приватный ключ
внутреннего WireGuard/AmneziaWG не установлен также как самостоятельная системная
зона. Неудача проверки — отказ: системная зона могла бы подняться напрямую при
загрузке и показать провайдеру адрес внутреннего сервера. Проверка не заменяет
общий белый список маршрутов: системный уровень сейчас не поддерживает
OpenConnect, а при его появлении проверка одного WG-ключа его не покроет. Она
не может запретить независимому администратору позже создать прямую системную
зону. Внутренний `ch` пока следует хранить только как пользовательскую зону с
`[Chain] Via = nl`, а не дублировать в `services.cellward.system.zones`.

Также при добавлении и подъёме пользовательской зоны проверяется её локальный
список зон в обоих направлениях: тот же WireGuard/AmneziaWG-ключ или тот же
OpenConnect-шлюз (адрес и порт) не может существовать одновременно в прямой и
цепочной пользовательской зоне. В случае OpenConnect это намеренно запрещает
даже разные учётные записи одного шлюза: прямой вход всё равно раскрыл бы
адрес. Это не решает проблему с *системным* OpenConnect-шлюзом и не заменяет
общую политику маршрутов; уже поднятую прямую зону последующее ручное
редактирование конфига не выключает.

## Жизненный цикл

Маршрут получает отдельный режим жизни, не смешанный с вопросом «можно ли его
подключить»:

- `demand` — поднимается при первом запуске программы или зависимого маршрута;
  после последнего потребителя закрывает все свои звенья и прекращает
  рукопожатия;
- `always` — запускается при загрузке и поддерживает соединение, пока его явно
  не отключат;
- возможно, `manual` — никогда не поднимается косвенно, но уже поднятым им можно
  пользоваться.

Общие префиксы цепочек считаются ссылками: если работают `nl` и `nl → ch`,
закрытие последней программы в `nl → ch` выключает только `ch`; `nl` остаётся,
пока у него есть свой потребитель. Авария любого обязательного звена закрывает
весь зависимый путь, без перехода на более короткий.

Текущие `connection = auto|ask|manual` и `system.zones.*.autoStart` покрывают
части этой модели, но не подсчёт потребителей и не выключение рукопожатий после
последней программы. `autoStart = true` у системной зоны сейчас означает именно
постоянный режим и потому не подходит внутреннему узлу вроде `ch`.

## Какая сеть считается локальной

Локальная сеть — не альтернативный default route. Это явно выбранный боковой
доступ к префиксам одного звена:

```text
Интернет:  café → home → vps
LAN:       none | café | home | vps
```

По умолчанию — `none`. Выбор `home` открывает только объявленные домашние
префиксы/сервисы (например, принтер), тогда как обычный интернет продолжает идти
через весь маршрут до `vps`. Несколько LAN одновременно требуют нескольких
явных правил; совпадающие адресные диапазоны — отказ, пока человек не выберет,
какому звену принадлежит диапазон. Автообнаружение текущей Wi-Fi LAN само по себе
не даёт к ней доступ: чужая сеть кафе не становится доверенной из-за RFC1918.

В схеме LAN рисуется боковой веткой от выбранного звена, а не частью основной
стрелки. Смена LAN не должна оставлять старые маршруты или сокеты: применяется та
же стена эпох, что при живой смене сети контейнера.

## Что видит каждое звено

Для каждого маршрута интерфейс показывает таблицу наблюдателей:

| Наблюдатель | Что видит |
|---|---|
| локальная сеть/провайдер входа | адрес первого звена, время и объём; не конечный сайт |
| внешний VPN | исходный адрес пользователя и адрес следующего звена; не трафик внутри него |
| промежуточный VPN/proxy | предыдущее звено и следующее назначение согласно своему месту |
| последнее звено | конечные IP и незашифрованные имена/данные только там, где их не защищает TLS |

Для каждого звена также показываются измеренный RTT и примерная добавка к
задержке. Сумма RTT — оценка, а не обещанный ping: маршруты провайдеров и нагрузка
могут сделать фактическую задержку другой.

## DNS

У DNS два разных назначения, и они не должны незаметно сливаться:

1. имя endpoint следующего звена разрешается через уже поднятый предыдущий hop;
2. DNS программ по умолчанию идёт через последнее звено маршрута.

DNS хоста не используется ни для одного из них. Разрешённый явно DNS другого
звена показывается как боковой выход на схеме и в таблице наблюдателей. Кэш
разделяется по маршрутам, чтобы ответ, полученный напрямую или через другую
цепочку, не переехал в защищённый маршрут.

Первая VPN-over-VPN реализация пока требует literal IP внутреннего endpoint:
это fail-closed ограничение до появления резолвера предыдущего hop, а не
разрешение спросить DNS хоста.
Интерактивный вход OpenConnect тоже запрещён внутри цепочки: его помощник пока
подключается к шлюзу из сети хоста до подъёма внешнего hop. В цепочке допускается
только вход через `PasswordFile` либо шлюз без входа (`AskLogin = no`).
Для одиночной зоны интерактивный вход передаёт клиенту уже полученный cookie
через stdin; адрес и сертификат шлюза закреплены по результату входа. Это не
снимает запрет на интерактивный вход для внутреннего звена цепочки.

## Stillconf и декларативная конфигурация

Stillconf сейчас не поднимает все зоны при чтении/`check`: матрица каналов
проверяет только уже поднятые зоны, а `fetch-via` поднимает явно выбранную.
Риск находится уровнем ниже: у системных зон Cellward `autoStart = true` по
умолчанию, и применение/загрузка системы запускает их.

Поэтому безопасность должна обеспечиваться Cellward: декларация узла `ch` не
публикует маршрут `ch`, внутренний узел не получает автозапуск, а запуск возможен
только как часть разрешённого `nl → ch`. Stillconf затем может показывать и
редактировать этот граф, но не является границей безопасности.
