# Маршруты, локальные сети и приватность цепочек

Черновик следующего этапа после первой цепочки `inner --via outer`. Его главное
правило: конфигурация подключения и разрешённый путь — не одно и то же.

## Пул узлов и разрешённые маршруты

В пуле могут лежать `home`, `nl`, `ch` и другие VPN/proxy-узлы, но программы
видят только явно опубликованные маршруты, например:

```text
home
nl
nl → ch
```

При таком наборе `ch` — внутренний узел: его нельзя поднять напрямую, выбрать в
пикере или автоматически запустить при загрузке. Конфигурация системы, Stillconf
и диагностические пробы не должны превращать наличие узла в разрешение маршрута.
Проверка графа выполняется до запуска первого звена; частично разрешённый путь
не запускается.

Первая реализация `cellward add inner inner.conf --via outer` хранит маршрут в
самой зоне и поддерживает только внешний системный VPN. Общий пул нужен, чтобы
один секрет/endpoint переиспользовался несколькими маршрутами без появления
нежелательного короткого пути.

## Жизненный цикл

Маршрут получает отдельный режим жизни, не смешанный с вопросом «можно ли его
подключить»:

- `demand` — поднимается при первом запуске программы или зависимого маршрута;
  после последнего потребителя закрывает все свои звенья и прекращает
  рукопожатия;
- `always` — запускается при загрузке и поддерживает соединение, пока его явно
  не отключат;
- возможно, `manual` — никогда не поднимается косвенно, но уже поднятым им можно
  пользоваться.

Общие префиксы цепочек считаются ссылками: если работают `nl` и `nl → ch`,
закрытие последней программы в `nl → ch` выключает только `ch`; `nl` остаётся,
пока у него есть свой потребитель. Авария любого обязательного звена закрывает
весь зависимый путь, без перехода на более короткий.

Текущие `connection = auto|ask|manual` и `system.zones.*.autoStart` покрывают
части этой модели, но не подсчёт потребителей и не выключение рукопожатий после
последней программы. `autoStart = true` у системной зоны сейчас означает именно
постоянный режим и потому не подходит внутреннему узлу вроде `ch`.

## Какая сеть считается локальной

Локальная сеть — не альтернативный default route. Это явно выбранный боковой
доступ к префиксам одного звена:

```text
Интернет:  café → home → vps
LAN:       none | café | home | vps
```

По умолчанию — `none`. Выбор `home` открывает только объявленные домашние
префиксы/сервисы (например, принтер), тогда как обычный интернет продолжает идти
через весь маршрут до `vps`. Несколько LAN одновременно требуют нескольких
явных правил; совпадающие адресные диапазоны — отказ, пока человек не выберет,
какому звену принадлежит диапазон. Автообнаружение текущей Wi-Fi LAN само по себе
не даёт к ней доступ: чужая сеть кафе не становится доверенной из-за RFC1918.

В схеме LAN рисуется боковой веткой от выбранного звена, а не частью основной
стрелки. Смена LAN не должна оставлять старые маршруты или сокеты: применяется та
же стена эпох, что при живой смене сети контейнера.

## Что видит каждое звено

Для каждого маршрута интерфейс показывает таблицу наблюдателей:

| Наблюдатель | Что видит |
|---|---|
| локальная сеть/провайдер входа | адрес первого звена, время и объём; не конечный сайт |
| внешний VPN | исходный адрес пользователя и адрес следующего звена; не трафик внутри него |
| промежуточный VPN/proxy | предыдущее звено и следующее назначение согласно своему месту |
| последнее звено | конечные IP и незашифрованные имена/данные только там, где их не защищает TLS |

Для каждого звена также показываются измеренный RTT и примерная добавка к
задержке. Сумма RTT — оценка, а не обещанный ping: маршруты провайдеров и нагрузка
могут сделать фактическую задержку другой.

## DNS

У DNS два разных назначения, и они не должны незаметно сливаться:

1. имя endpoint следующего звена разрешается через уже поднятый предыдущий hop;
2. DNS программ по умолчанию идёт через последнее звено маршрута.

DNS хоста не используется ни для одного из них. Разрешённый явно DNS другого
звена показывается как боковой выход на схеме и в таблице наблюдателей. Кэш
разделяется по маршрутам, чтобы ответ, полученный напрямую или через другую
цепочку, не переехал в защищённый маршрут.

Первая VPN-over-VPN реализация пока требует literal IP внутреннего endpoint:
это fail-closed ограничение до появления резолвера предыдущего hop, а не
разрешение спросить DNS хоста.

## Stillconf и декларативная конфигурация

Stillconf сейчас не поднимает все зоны при чтении/`check`: матрица каналов
проверяет только уже поднятые зоны, а `fetch-via` поднимает явно выбранную.
Риск находится уровнем ниже: у системных зон Cellward `autoStart = true` по
умолчанию, и применение/загрузка системы запускает их.

Поэтому безопасность должна обеспечиваться Cellward: декларация узла `ch` не
публикует маршрут `ch`, внутренний узел не получает автозапуск, а запуск возможен
только как часть разрешённого `nl → ch`. Stillconf затем может показывать и
редактировать этот граф, но не является границей безопасности.
