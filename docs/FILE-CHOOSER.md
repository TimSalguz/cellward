# FileChooser: доверенный backend

Это первый безопасный слой, не файловый менеджер и не замена
`org.freedesktop.portal.FileChooser`. Существующий `bus_filter` по-прежнему
пропускает FileChooser и FileTransfer в xdg-desktop-portal. Новый production
D-Bus service здесь не регистрируется.

## Граница доверия и views

Backend работает на хосте. Identity вызывающего он получает только от broker,
который определяет её по pidfd и namespaces (`broker`, `origin`, `place`), а не
из app-id, пути или текста запроса. `Who::Unknown` не получает view.

Тип `View` различает три разных пространства, которые нельзя склеивать по
строковому совпадению путей:

- `AppFs` — эффективная файловая система текущего контейнера: его собственный
  дом, layer/overlay и уже выданные folder mounts. Доступен самому контейнеру.
- `HostHome` — настоящий дом пользователя. Требует отдельного явного решения
  policy; существование dirfd или знание пути таким решением не является.
- `OtherContainer(name)` — хранилище другого контейнера. Требует доверенного
  выбора именно этого контейнера для текущего запроса, а не только права
  открыть произвольный путь.

`ViewRoots` содержит уже открытые доверенным backend dirfd. `Policy` по
умолчанию запрещает HostHome и все OtherContainer. Авторизация возвращает
`AuthorizedView`, привязанный к identity и конкретному root; resolver принимает
только этот объект.

## Resolver и передача результата

Путь внутри view — относительный. Абсолютные пути и `..` отклоняются. Каждый
компонент открывается через `openat` от предыдущего dirfd с `O_NOFOLLOW`;
symlink, включая последний компонент, не следуется. Поэтому смена symlink не
может увести resolver за root. У конечного объекта до и после открытия
сверяются `(st_dev, st_ino)` и тип: подмена между проверкой и открытием —
ошибка. Уже открытый dirfd остаётся capability на тот же inode, даже если его
позже переименуют. Hardlink неотличим от обычного файла; границу против
одно-uid процессов, которые могут создавать такие ссылки в обоих местах, этот
resolver не заменяет.

Выбор обычного файла передаётся как fd (`FdGrant`, позже `SCM_RIGHTS`), либо
регистрируется в Document Portal с последующей выдачей portal URI/fd. Raw dirfd
приложению не выдаётся: после передачи каталога resolver больше не мог бы
запретить обход symlink внутри него. Directory export через Document Portal —
отдельная следующая интеграция. Путь сам по себе новым разрешением не является.
Grant помнит identity, view и read-only/read-write
режим; дескриптор можно продублировать только для той же identity.
`GrantRevocation` закрывает выдачу новых копий. Уже переданные Unix fd, как и
открытые cwd/mount у существующих `grants`, этим не отзываются: для них нужны
завершение процесса, Document Portal revoke и существующее отмонтирование
folder grants соответственно. Этот слой не обещает невозможного.

Document Portal пока не вызывается. При последующей интеграции срок жизни
экспорта и отзыв документа должны быть связаны с `GrantRevocation`; нельзя
молча превращать одноразовый выбор в постоянный folder grant.

## Overlay mapping

AppFs root открывается на эффективном merged/pinned view, а не на host `upper`
или `work` из `folder_rules`. Запись в overlay идёт в его merged view; ни
`upper/work`, ни нижний источник не выдаются под видом AppFs. Для
OtherContainer используется отдельно авторизованный root его хранилища.
Отображение будущего portal URI во внутренний путь выполняет backend по этой
же typed view, а не `canonicalize` произвольной строки. Существующие
`folder_rules::{prepare_for_launch,bwrap_args}` остаются владельцами mount и
overlay mapping.

## Административный view — отдельно

Root-picker не входит в обычный FileChooser. Если понадобится admin view, это
будет отдельный backend и отдельная явная операция через polkit с его собственной
авторизацией и аудитом. Обычный picker никогда не принимает и не пересылает
sudo-пароль, не повышает привилегии и не открывает `/` по просьбе приложения.
