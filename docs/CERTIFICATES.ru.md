# Доверенные сертификаты по контейнерам — дизайн

English: [CERTIFICATES.md](CERTIFICATES.md) · Опирается на
[CONTAINERS.ru.md](CONTAINERS.ru.md) · Модель угроз: [LEAK-MODEL.md](LEAK-MODEL.md)

**Статус: предложение (2026-09-17).** Не реализовано. Факты из §2 проверены на
бинарях актуального nixpkgs 2026-09-17; пункты с пометкой *проверить* —
первое, что обязан подтвердить прототип в VM.

## 1. Цель и угроза

Некоторые сети требуют доверять дополнительному корневому сертификату:
национальному УЦ, которым подписаны госсервисы, корпоративному корню
TLS-инспекции, тестовому УЦ. Владелец закрытого ключа доверенного корня
**читает и подменяет любое TLS-соединение** любой программы, которая ему
доверяет: пароли, переписку, банковские сессии. Поэтому:

> Дополнительному корневому сертификату доверяют программы тех контейнеров, в
> которые он добавлен, — **и больше ничто**: ни хост, ни соседний контейнер, ни
> следующий запуск той же программы без этого контейнера. Добавление — громкое,
> удаление — одно действие.

Чем это не является: способом заставить хост доверять УЦ (это
`security.pki.certificates` в NixOS, и мы сознательно делаем другое) и защитой
от УЦ, которому хост уже доверяет.

## 2. Где TLS-стеки ищут корни доверия

Корневой сертификат что-то значит только для кода, который его читает. Таблица —
инвентарь того, что дизайн обязан покрыть. «Бандл» — это
`/etc/ssl/certs/ca-certificates.crt`; в NixOS это цепочка симлинков, кончающаяся
одним файлом пакета `nss-cacert` в store (тот же файл стоит за
`/etc/ssl/certs/ca-bundle.crt` и `/etc/pki/tls/certs/ca-bundle.crt`).

| потребитель | откуда берёт корни (NixOS) |
|---|---|
| OpenSSL (nixpkgs) | `NIX_SSL_CERT_FILE` (патч nixpkgs), `SSL_CERT_FILE`/`SSL_CERT_DIR`, затем бандл |
| GnuTLS (GLib/GIO, WebKitGTK, Wine) | бандл, плюс системное доверие `pkcs11:` — p11-kit |
| модуль доверия p11-kit | вкомпилированный список путей: `/etc/ssl/trust-source`, бандл, `/etc/pki/tls/certs/ca-bundle.crt`, `/var/lib/ca-certificates/ca-bundle.pem`, `/etc/ssl/cert.pem` |
| NSS (nixpkgs) | модуль встроенных корней `libnssckbi.so` **— симлинк на `p11-kit-trust.so`** → список выше; плюс база пользователя/профиля (`cert9.db`) |
| Firefox (сборка nixpkgs) | системный NSS → p11-kit → бандл; `cert9.db` профиля; корпоративные политики |
| бинарные производные Firefox со своим NSS (например Zen, Tor Browser) | собственные вкомпилированные корни Mozilla; `cert9.db` профиля; политики |
| Chromium, Chrome, Electron | Chrome Root Store (встроен); локально доверенные корни из базы NSS `~/.pki/nssdb`. Считается ли модуль корней p11-kit локальным доверием — *проверить* (ожидается: нет) |
| curl, git, nix (nixpkgs) | `NIX_SSL_CERT_FILE`, `CURL_CA_BUNDLE`, `GIT_SSL_CAINFO`, бандл |
| Python | `ssl` → OpenSSL; `requests` → `REQUESTS_CA_BUNDLE`; `certifi` из nixpkgs → `NIX_SSL_CERT_FILE` |
| Node.js, Bun | вкомпилированные корни Mozilla + `NODE_EXTRA_CA_CERTS` (читается один раз при старте) |
| Go | `SSL_CERT_FILE`, `SSL_CERT_DIR`, затем бандл |
| Rust `rustls-native-certs` / `webpki-roots` | `SSL_CERT_FILE` и бандл / **вкомпилированы, недостижимы** |
| Java | собственный `cacerts` JDK; `javax.net.ssl.trustStore` |
| .NET, Qt | OpenSSL → как OpenSSL |
| приложения Flatpak, runtime Steam, AppImage | `/etc/ssl` своего runtime — **снаружи недостижимо** |

Два вывода задают дизайн:

1. **В NixOS большую часть доверия несёт один файл**: бинд расширенного бандла
   поверх него достаёт OpenSSL, GnuTLS, p11-kit, а через них системный NSS и
   Firefox из nixpkgs — на любом языке, который ими пользуется.
2. **Chromium/Electron и бинарным форкам Firefox нужны их базы NSS**, а живут
   они в доме — ровно там, где и случилась бы утечка на хост, если база не
   принадлежит контейнеру.

## 3. Дизайн

### 3.1 Хранение

- Сертификат принадлежит **контейнеру** — никогда зоне, программе или хосту.
  Декларативные приходят из `containers.<имя>.trust.certificates` (список
  путей; публичный сертификат УЦ в store — это нормально), локальные копируются
  в состояние контейнера командой `vpn-zone trust add`.
- При добавлении файл разбирается и отвергается, если это не один сертификат
  PEM или DER с `basicConstraints CA:TRUE`. Хранится по отпечатку SHA-256:
  `…/trust/<sha256>.pem`. Разбор и отпечатки — через `openssl x509` из
  манифеста (кода X.509 и хеширования в крейте нет).
- Держать сертификаты могут только контейнеры со своим домом: `private` и
  `overlay` с гарантированно отдельными слотами NSS (§3.4). **Без контейнера
  (основной дом) — нельзя**: его базы NSS — это базы хоста.

### 3.2 Слой 1 — бандл (в mount namespace запуска)

В `profile-run`, после слоя дома и до старта программы
([CONTAINERS.ru.md](CONTAINERS.ru.md) §3.3):

1. собрать расширенный бандл: байты бандла хоста на момент запуска (файл, на
   который указывает `NIX_SSL_CERT_FILE` или `SSL_CERT_FILE`, если заданы,
   иначе разрешённый системный бандл), а следом сертификаты контейнера; записать
   в tmpfs, смонтированный поверх приватного runtime-пути контейнера;
2. для каждого существующего пути из списка p11-kit и привычных путей бандла
   пройти цепочку симлинков руками (`sys::link_target`, как для `resolv.conf`,
   [GOTCHAS](GOTCHAS.md) §3) и забиндить расширенный бандл поверх **каждой
   различной цели** — в NixOS это один файл в store;
3. `/etc/ssl/trust-source` не трогать: этот слой только добавляет.

Бинд поверх файла в store заодно покрывает программы, которые называют
`${cacert}/etc/ssl/certs/ca-bundle.crt` напрямую. bwrap биндит `/nix/store` и
`/etc` рекурсивно, поэтому `private`-контейнер видит тот же бинд.

### 3.3 Слой 2 — окружение

`SSL_CERT_FILE`, `NIX_SSL_CERT_FILE`, `CURL_CA_BUNDLE`, `REQUESTS_CA_BUNDLE`,
`GIT_SSL_CAINFO` и `NODE_EXTRA_CA_CERTS` получают значение
**`/etc/ssl/certs/ca-certificates.crt` — системный путь**, и никогда путь
контейнера.

Это самое важное решение документа. Переменные окружения утекают: программа в
контейнере может выполнить `systemctl --user import-environment` или
`dbus-update-activation-environment --all`, и с этой минуты их унаследует любой
пользовательский сервис. С системным путём такая утечка безвредна: за пределами
mount namespace контейнера этот путь — обычный бандл хоста. Специфичное для
контейнера **содержимое** приходит только из монтирования, а монтирование утечь
не может.

### 3.4 Слой 3 — базы NSS

Для Chromium/Electron (`~/.pki/nssdb`) и профилей семейства Firefox (`cert9.db`
рядом с `prefs.js` под известными корнями профилей): `certutil -A -t "C,," -n
"vpn-zones <префикс отпечатка>"` — его запускает `profile-run` в mount namespace
запуска до старта программы, `certutil` берётся из `nss.tools` через манифест.

- **База пишется, только если доказано, что она — контейнера.** Перед записью
  `profile-run` читает `/proc/self/mountinfo` и проверяет, что путь лежит на
  только что смонтированном оверлее или на бинде приватного дома. Всё прочее —
  каталог профиля, который оверлей не накрывает (`~/.zen` не входит в
  XDG-слоты), — пропускается с громким предупреждением, где названа программа и
  предложен контейнер со своим домом. Это та самая проверка, что стоит между
  сертификатом и хостом.
- **Ловушка, которую это обходит.** Слот оверлея накладывается, только если
  каталог на хосте существует ([GOTCHAS](GOTCHAS.md) §5). На машине без
  `~/.pki` вызов `certutil -d sql:$HOME/.pki/nssdb` внутри контейнера создал бы
  базу **в настоящем доме** — и Chromium хоста с этой минуты доверял бы
  сертификату. Поэтому контейнеры с доверием создают недостающие нижние
  каталоги (пустыми, mode 0700) до наложения слоёв, а всё, что проскочит,
  ловит проверка mountinfo.
- Идемпотентно: файл-штамп в каталоге базы хранит отпечатки установленных
  сертификатов; штамп совпал → `certutil` не запускается вовсе.
- Первое копирование вверх отделяет базу контейнера от базы хоста на тот
  момент; последующие изменения хоста внутри не видны. Ожидаемо и описано.
- Удаление (§3.6) вызывает `certutil -D` для каждого прописанного в штампе
  имени; у дома `private` — прямо с хоста по каталогу контейнера, у `overlay` —
  при следующем запуске (писать в верхний слой смонтированного оверлея снаружи —
  неопределённое поведение).

### 3.5 Рассмотрено и по умолчанию не используется

- **Корпоративные политики Firefox** (`Certificates.Install` в
  `/etc/firefox/policies/policies.json` или `distribution/policies.json`):
  покрывают свежие профили, но бинд поверх существующего `policies.json`
  заменяет собственные политики человека, а слияние — это переписывание не
  нашего файла. Возможно позже, явной опцией контейнера для бинарных форков.
- **Политика Chromium `CACertificates`** в `/etc/chromium/policies/managed/`:
  *проверить* наличие в закреплённой версии Chromium; то же возражение «не наш
  файл».
- **Java**: по желанию для контейнера, этап 2. Хранилище PKCS#12 из
  расширенного бандла через `openssl pkcs12 -export -nokeys -jdktrust
  anyExtendedKeyUsage` и `JAVA_TOOL_OPTIONS=-Djavax.net.ssl.trustStore=…` с
  путём, существующим только в mount namespace контейнера. Утечёт переменная —
  Java на хосте не найдёт хранилище: ошибки TLS, а не доверие.
- **Режим замены** («доверять только этому УЦ»): потребовал бы затенить все
  источники доверия, включая `trust-source`, и всё равно не убрал бы Chrome
  Root Store. Вне рамок.

### 3.6 Интерфейс

CLI:

```
vpn-zone trust add <контейнер> <файл.pem>     # на терминале спросит подтверждение
vpn-zone trust list [<контейнер>] [--json]
vpn-zone trust rm <контейнер> <префикс sha256>
vpn-zone trust reset <контейнер>               # все дополнительные сертификаты
```

GUI, добавление (выбор файла, затем один диалог):

- субъект, издатель, срок действия, отпечаток SHA-256, ограничения имён, если
  есть;
- предупреждение словами, а не сноской: «Любой, у кого есть закрытый ключ
  этого сертификата, сможет читать и подменять зашифрованный трафик программ
  контейнера «X»: пароли, переписку, банковские сессии. На хост и в другие
  контейнеры сертификат не попадёт»;
- подтверждение вводом имени контейнера — так же, как удаление зоны
  переспрашивает вторым шагом.

Везде, где виден контейнер, — знак ⚠ и «дополнительный корневой сертификат»:
в строках пикера, в `vpn-zone container list`, в `status --json`
(`trust.extra[]`) и в `doctor`. Сброс — один пункт меню: «Сбросить доверенные
сертификаты».

Модуль (для nix_cm): `containers.<имя>.trust = { certificates = [ … ];
acknowledgeRisk = true; nss = true; java = false; }`. Проверка при вычислении
отвергает непустой `certificates` без `acknowledgeRisk`.

## 4. Поведение при сбоях

- Бинд бандла (слой 1) не удался → **запуск останавливается** с причиной.
  Программа, которая по ожиданию человека доверяет сертификату, а на деле молча
  нет, — это сломанный запуск, и «запустить без слоя» не должно быть путём
  кода, на который можно попасть случайно.
- Базу NSS не удалось доказать приватной → эта база пропускается с
  предупреждением; запуск продолжается (слой 1 всё равно действует).
- Файл сертификата пропал или не разбирается при запуске → запуск
  останавливается.

## 5. Куда теперь может утечь доверие?

- **Хост.** Бандл хоста не меняется никогда; бинды живут в mount namespace
  запуска; переменные окружения называют только системный путь (§3.3); базы
  NSS пишутся только после проверки mountinfo (§3.4).
- **Соседний контейнер в той же зоне.** У каждого запуска контейнера свой mount
  namespace; в namespace зоны ничего не монтируется.
- **Та же программа вне контейнера.** Делегированный или брокерский запуск
  стартует в mount namespace и окружении хоста — биндов нет, а переменные,
  которые он мог унаследовать, называют системный путь.
- **Подсадка в одноразовый контейнер** (`--tmp-profile --join`): доверие
  принадлежит контейнеру, поэтому у всех жильцов набор одинаковый — ни больше,
  ни меньше.
- **Дочерний процесс, уходящий в другую зону**, идёт через делегирование или
  брокер и стартует снаружи: наследования нет.
- **Программы, до которых не дотянуться** (§2: Flatpak, runtime Steam, AppImage,
  вкомпилированные корни), сертификата не получат. Это не утечка, а граница;
  `doctor` называет такие программы контейнера, когда может их распознать.

## 6. Тесты

Всё — с УЦ, сгенерированным на лету (`openssl req -x509 …`), и серверным
сертификатом для `tls.internal`, подписанным им; ничего настоящего и ничего с
хоста. В `tests/vm.nix`, на машине `machine`:

1. **Контейнер A доверяет.** TLS-сервер на loopback внутри offline-зоны; в
   контейнере A (с УЦ) `openssl verify`, `curl --resolve
   tls.internal:8443:127.0.0.1 https://tls.internal:8443` и
   `certutil -L -d sql:$HOME/.pki/nssdb -n …` успешны; `trust list` (p11-kit)
   показывает УЦ.
2. **Контейнер B в той же зоне — нет.** Те же команды, все неуспешны.
3. **Хост — нет.** `openssl verify` и `curl` на хосте неуспешны; хеши
   `~/.pki/nssdb` хоста и `/etc/ssl/certs/ca-certificates.crt` до и после
   совпадают.
4. **Утечка окружения безвредна.** Изнутри A: `systemctl --user
   import-environment SSL_CERT_FILE NIX_SSL_CERT_FILE`; после этого
   `systemd-run --user --wait openssl verify …` на хосте по-прежнему неуспешен.
5. **Нет `~/.pki` на хосте.** Оверлей-контейнер с УЦ на доме без `~/.pki`:
   сертификат оказывается в верхнем слое контейнера, а в доме хоста базы с ним
   нет.
6. **Сброс.** После `vpn-zone trust reset A` тест 1 неуспешен.
7. **Сбой — это отказ.** Контейнер с пропавшим файлом сертификата не стартует.
