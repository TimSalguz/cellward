# Контейнеры и разрешения: целевая модель

Документ дизайна (владелец, 2026-09-25). Здесь — куда идём. Что уже сделано —
в CHANGELOG, что закрыто и что открыто по безопасности — в `LEAK-MODEL.md`
(§17–§19). Реализация по шагам, в конце — порядок.

## 1. Главная единица — контейнер, а не программа

Контейнер — это место, где живут программы: у него своя **сеть** (без сети,
«напрямую», одна из VPN), своё **хранилище** (дом), свои **разрешения**
(папки, микрофон, камера), свой **цвет рамки** и список **программ**. Модель
близка к Qubes OS, только без ВМ.

**Лаунчер от контейнеров.** Открываешь его — видишь контейнеры: «Работа ·
через VPN-1», «Банк · напрямую», «Без сети». У каждого:

- его программы — запуск в одно нажатие, без вопросов;
- «Настройки» — сеть, выданные папки, микрофон и камера, цвет рамки;
- «Открыть хранилище» и «Добавить программу».

Ярлыки в меню системы остаются: они запускают программу в её контейнере.

**Незнакомая программа** ни о чём не спрашивает при запуске: она стартует в
своём новом контейнере **без сети** — правдоподобная пустота для сети, — и
одновременно уведомление: «X запущена без сети. [Выбрать сеть] [В другой
контейнер]». Выбор меняет контейнер, а не одну программу. Сеть контейнера
потом меняется в его настройках — в идеале на ходу, без перезапуска программ
(ROADMAP: смена сети контейнера на ходу).

## 2. Хранилище: свой дом у каждого контейнера

Стандарт — **песочница**: у контейнера пустой собственный дом, настоящего
дома он не видит вовсе; настоящие папки — только выданные (`container
grant`, в том числе на срок и на ходу — уже есть). Слой над настоящим домом
(overlay, «читает настоящие файлы, пишет в свой слой») остаётся как явный
выбор для тех, кому он удобнее.

**Обратное направление — человеку.** Дом каждого контейнера виден на хосте,
например `~/Контейнеры/<имя>/`: положил файл — контейнер видит, скачал он —
видишь ты. Зонам это хранилище не видно (проверка — перечень сокетов и путей
`doctor`).

## 3. Разрешения: «как Android, но с подменой»

Программа **не узнаёт об отказе**. До разрешения она получает то, что выбрано
для этого ресурса в этом контейнере:

| поведение до разрешения | микрофон | камера | файлы | сеть |
|---|---|---|---|---|
| **нет устройства** | микрофона в системе нет | камеры нет | — | — |
| **пустота** (стандарт) | тишина | чёрный кадр | пустой дом | без сети |
| **модуль-имитатор** | шум, запись, синтез | шум, аватар | — | — |
| **настоящее** | после «разрешить» | после «разрешить» | выданные папки | сеть контейнера |

При первой попытке — **уведомление** с кнопками («разрешить один раз /
всегда»), и строка в меню окна («микрофон: тишина / настоящий»): подмена не
должна обманывать человека, только программу. После «разрешить» поток
переключается на настоящий **на ходу** — звонок продолжается без перезапуска.

Разрешение даёт не программа, а политика **вне зоны**: связи PipeWire
(WirePlumber решает, к какому источнику подключить поток зоны), привязки
каталогов (mount в пространстве зоны). Прямой доступ к устройствам зоне закрыт
(`/dev/snd`, камеры — LEAK-MODEL §19), иначе разрешение ничего бы не держало.

## 3д. Экран: трансляция и снимки

**Сейчас** (LEAK-MODEL §21): молча снять экран нельзя. Протоколы захвата
Wayland зоне не видны, IPC композитора закрыт, портал снимков отказан.
Трансляция идёт только через портал ScreenCast, и по умолчанию его диалог
выбора показан **каждый раз**: запомнить выбор программа не может. Так же на
Android: вопрос перед каждым захватом экрана.

**Выключатель на зону — сделано (2026-09-25):** `cellward screencast <зона>
ask (по умолчанию)|yes|no`, Nix `programs.cellward.screencast.<зона>`, поле
`screencast` в `status --json`. Устроен как у микрофона: Nix важнее своей
настройки зоны, без обеих — `ask`. Фильтр шины герметичной зоны читает его
на каждый вызов, поэтому новое значение действует сразу.

- `ask` — стандарт: диалог портала каждый раз, выбор не запоминается.
- `no` — отказ на каждый вызов портала ScreenCast, с объяснением для
  программы и строкой в `cellward journal`. Позже — подмена: поток с окнами
  только этого контейнера или чёрный экран.
- `yes` — выбор можно запомнить: следующую трансляцию портал начнёт без
  диалога. Только если портал знает зону по имени (см. ниже, LEAK-MODEL
  §23), иначе — как `ask`: выбор не хранится за безымянной программой,
  общей для всех зон. В песочнице файлов — тоже как `ask`.
- Программы негерметичной зоны говорят с порталом напрямую, мимо
  выключателя.

**Дальше — в общую модель разрешений:**
- **Снимок по вопросу.** Сейчас программы со «снимком области» в зоне не
  работают. Вариант — пропускать портал Screenshot только в интерактивном
  режиме, если диалог портала есть в этом окружении. Иначе — наш вопрос,
  как у микрофона. Неинтерактивный снимок — никогда.
- **Видно, что идёт трансляция.** Фильтр видит, как портал начинает и
  закрывает сессию. Пока трансляция идёт: уведомление, метка в меню окна
  («● экран») и кнопка «остановить», которая закрывает сессию портала.
- **Чужие окна в трансляции.** Если зона транслирует весь экран, в
  уведомлении сказано, что туда попадут окна других зон.
- **Рамка в трансляции.** Её цвет и заголовок выдают зону собеседнику.
  Решение — «рамка скрыта, пока окно транслируется». Для этого композитор
  должен сообщать посреднику о трансляции (niri этого не умеет: есть только
  правило `is-window-cast-target`). Это кандидат в патч niri (WINDOW-FRAME).
  Пока есть `cellward frame title off` на зону.
- **Хост транслирует окно зоны.** Это решение хоста, зона его не видит и не
  запрещает.

**Проверено (2026-09-25):** в xdg-desktop-portal владельца (1.22) реестр
хостовых программ есть — `org.freedesktop.host.portal.Registry.Register`,
один раз на соединение, до первого вызова портала. Программам зоны он
закрыт (иначе программа назвалась бы чужим именем, LEAK-MODEL §23).

**Сделано (2026-09-25):** фильтр сам регистрирует каждое соединение зоны
как `cellward.zone.<id>` до того, как пропустит первый вызов программы
(LEAK-MODEL §23). Портал различает зоны и хранит решения по каждой, а
диалог показывает имя «cellward · <зона>» и значок из ярлыка, который
держатель зоны кладёт в `~/.local/share/applications`. Форк портала не
понадобился. Портал без реестра (старше 1.19) — всё как раньше, без имени.

## 3е. Срок разрешения

**Есть сейчас:**

| ресурс | как долго |
|---|---|
| каталоги песочницы | навсегда или на срок (`grant … --for 30m\|2h\|7d`, в GUI — час, сутки, неделя). В конце срока каталог отмонтируется и у уже запущенных программ, в журнале — `grant-expired` |
| микрофон | «один раз» — одна запись (один поток); «всегда» — зоне навсегда; после отказа зону не спрашивают паузу `ask-again` (3m по умолчанию, 30s…1d; Nix `askAgainAfter`) |
| трансляция экрана | `ask` — каждый раз заново; `yes` — пока портал помнит выбор (зона или контейнер с именем у портала: `cellward.zone.<id>`, `cellward.c.<id>`); `no` — никогда (LEAK-MODEL §21) |
| камера, nix-daemon, файлы хоста | только вкл/выкл, без срока |
| аварийный ключ (сеть хоста) | 15 минут |

**Цель — одни и те же сроки для любого разрешения**, как на Android, плюс
срок по часам:

- **один раз** — одна запись, один кадр, одна трансляция;
- **пока открыт контейнер** — до выхода последней его программы;
- **на время** — 30 минут, час, сутки, неделя;
- **всегда**.

В конце срока разрешение снимается на ходу. Микрофон переключается на
тишину, камера — на чёрный кадр, каталог отмонтируется (как сейчас). Всё это
видно в меню окна («микрофон: настоящий, ещё 42 мин») и в журнале. Счётчик
(«3 раза») не нужен: «один раз» и срок по часам покрывают то же, а человеку
понятнее. Нужен — добавить можно в ту же запись.

Где хранится: так же, как выдача каталога на срок — строка с концом срока в
настройке контейнера (`until=<секунды>`). Строку, которую старая версия не
поймёт, она прочтёт как отказ.

## 3а. Сетевой фильтр контейнера

Сеть контейнера — не только «какая зона», но и **куда можно**. Три режима:

- **открыто** — всё через сеть зоны, как сейчас;
- **список разрешённого** — адреса, сети, порты и **имена** (`example.com`,
  `*.corp.internal`): DNS-пересыльщик зоны, получив ответ на разрешённое имя,
  кладёт его адреса в набор nftables (как dnsmasq с ipset) — единственный
  способ разрешать сайты за CDN;
- **спрашивать** («параноидальный», как Comodo): новое соединение
  задерживается (NFQUEUE в сетевом пространстве зоны), и через единую точку
  вопросов — «Firefox в контейнере Работа хочет example.com (93.184.215.14),
  443. [Один раз] [Всегда для example.com] [Никогда]»; имя известно по DNS-
  запросу, который видел пересыльщик.

**Контейнеры одной зоны** делят её сетевое пространство; различаются по cgroup:
каждый контейнер запускается в свой срез systemd, nftables сопоставляет сокет
с ним (`socket cgroupv2`). Тот же срез несёт ресурсы контейнера (память,
процессор, число процессов) — общая основа.

**Подмена и здесь**: до ответа соединение ждёт, как на медленной сети;
«никогда» — пакеты молча отбрасываются; запрет неотличим от плохой сети.
Фильтрует ядро в пространстве зоны, менять его программам зоны нечем.

**Оговорки**: программа со своим DNS поверх HTTPS идёт мимо пересыльщика — для
неё остаются адреса; в режиме «спрашивать» известные DoH-серверы по умолчанию
не разрешены, и браузер откатывается на системный DNS. По адресам сайты за
CDN почти неразличимы — основной путь имена.

## 3б. Маршрут по назначению

Не только «пускать или нет», но и **через какой выход** — раздельная
маршрутизация на уровне контейнера. Правила по назначению:

- **страна** — «адреса России → напрямую, остальное → VPN»: списки адресов по
  странам — пакетом в Nix (базы GeoIP вроде v2fly/geoip или db-ip),
  закреплены в store, без скачивания на ходу; нет списка — всё по VPN
  (fail-closed);
- **имена** — `*.ru`, конкретные сайты → напрямую (через DNS-пересыльщик зоны,
  как в §3а);
- **локальная сеть** — принтер, NAS, роутер → через хост; переключатель
  «видеть локальную сеть».

**Выходы**: любая зона (VPN), «напрямую», «заблокировать»; позже — «напрямую
через zapret» (§3в).

**Как.** У сетевого пространства зоны — два интерфейса: туннель и прямой выход
через pasta, как у простой зоны; nftables метят соединения по наборам адресов,
маршрутизация по меткам ведёт их в свой выход. Решает ядро в пространстве
зоны.

**Гибрид — именованная сеть в общем списке.** Правила собираются в сеть с
именем и честной подписью и выбираются у контейнера, как любая другая: рядом
с «Без сети», «VPN-1», «VPN-2» — «Гибрид 1: RU напрямую, остальное через
VPN-1 — менее безопасно». Пометка «менее безопасно» — везде, где видна сеть:
лаунчер, `status`, меню окна; в заголовке рамки — особый знак (например «½»):
по окну видно, что часть трафика идёт мимо VPN. У гибрида в списке сразу
видно, **через какие интерфейсы и выходы он может идти** («Гибрид 1 → eth0
напрямую · wlan0 через VPN-1»), а на блок-схеме (§3г) это его ветки — с
правилом над каждой.

**Честно и видно.** Это сознательная дыра в «всё через VPN»: `status`,
`doctor` и меню окна говорят «часть трафика напрямую», правила перечислены.
DNS раздваивается: имена прямого выхода разрешаются прямым резолвером (иначе
CDN отдаст адрес не той страны) — эти запросы видит провайдер, так и задумано.
Снаружи по адресам видно, что машина ходит и напрямую, и через VPN; по
умолчанию выключено, включается у контейнера.

## 3в. zapret (потом)

Вид выхода: простая зона, трафик которой проходит через обработчик zapret
(nfqws) в её собственном выходе, — и тогда это ещё один выход в списке §3б.
Правила обхода сложны и меняются вслед за блокировками — отдельная работа.

## 3г. Выходы как граф: цепочки и блок-схема

С раздельным маршрутом у контейнера несколько выходов, а у выхода — свой путь
наружу: это граф, и показывать его честнее блок-схемой. В этой модели «зона»
по сути — **выход**: контейнеры пользуются выходами, выходы соединяются
стрелками «идёт через».

```
контейнер «Работа» ──правила──┬─ *.ru, адреса RU ──► напрямую ─────────► eth0
                              ├─ локальная сеть ───► напрямую ─────────► eth0
                              └─ остальное ────────► VPN-2 ─через─► VPN-1 ─через─► wlan0
контейнер «Банк» ─────────────────────────────────► напрямую + zapret ─► eth0
контейнер «Без сети» ──────────────────────────────► (нет выхода)
```

**Узлы**: интерфейсы хоста (есть: зона через интерфейс); VPN — WireGuard,
AmneziaWG, OpenConnect — через любой другой выход (есть частный случай: зона
через системную зону); прокси (SOCKS, HTTP, VLESS…) — адаптером вроде sing-box
или tun2socks в выходе зоны превращаются в интерфейс; zapret; «заблокировать»;
«нет сети». В Nix — например `exits.vpn2 = { type = "wireguard"; via =
"vpn1"; }`.

**Безопасность цепочек:**

- **никакого отката на прямой путь**: упал любой узел — падает вся цепочка, её
  контейнеры без сети;
- циклы и ссылки на несуществующее отвергаются при сборке;
- MTU считается по всей цепочке (каждый уровень его уменьшает — иначе крупные
  пакеты тихо пропадают);
- VPN разных провайдеров в цепочке — реальная приватность (первый видит вас,
  но не назначение; последний — назначение, но не вас), цена — задержка;
- блок-схема в окне — это и проверка: видно, куда реально пойдёт трафик;
  `doctor` сверяет схему с тем, что на деле в сетевых пространствах.

## 4. Модули-имитаторы

Модуль — **обычный источник PipeWire** (Audio/Source, Video/Source) с
известным именем. Наша политика ничего не генерирует сама — она только
выбирает, к чему подключить поток зоны: к пустоте, к модулю или к настоящему
устройству. Авторам модулей не нужно знать о cellward; в настройке
контейнера указывается имя узла:

```nix
programs.cellward.containers.work.microphone.before = "silence"; # absent | silence | "<узел>"
```

**Модуль — чужой код**, поэтому он работает в своей зоне без сети: ни
настоящего микрофона, ни сети, ни дома у него нет. Политика гарантирует, что
модуль только отдаёт звук или кадр и никогда не подключается к настоящим
устройствам. Плохой модуль в худшем случае даёт плохую подделку, но ничего не
выносит.

## 5. Программы, которые знают о нас

Узнать, что они в контейнере, программы могут и сейчас (`VPN_ZONE_CURRENT`,
в песочнице `/.flatpak-info`). Для адаптированных — честный путь: интерфейс
D-Bus (рабочее имя `org.vpnzones.Permissions`), чтобы попросить явно: «дай
микрофон», с объяснением зачем; человек отвечает, как на Android.

Интерфейс **не выдаёт отказа**: ответ «нет» для программы выглядит так же,
как подмена — она узнаёт, что ей дали, а не что ей отказали. Иначе программы
смогут требовать разрешения и отказываться работать без них.

## 6. Где живут настройки: рамки Nix и местные решения

Настройки есть и в Nix (через nix_cm), и местные (лаунчер, окна-вопросы) — у
каждой видно, откуда она (`source`: `nix` / `local` / `default`). Правило:

- **Nix задаёт рамки и умолчания**: умолчания (новая программа — без сети,
  микрофон — «спрашивать»), **жёсткие запреты** («зоне Банк микрофон
  никогда», «этот контейнер только через VPN-1») — их не переопределить ни в
  лаунчере, ни в окне-вопросе, — и то, что должно переезжать на другую машину
  вместе с конфигурацией (контейнеры, их сети и программы);
- **местное — решения внутри рамок**: «микрофон этой зоне всегда», «выдать
  папку», «сменить сеть» — мгновенно, без пересборки (на вопрос о микрофоне
  во время звонка пересборкой не ответить);
- **мостик**: nix_cm видит местные решения и предлагает **закрепить** их в
  конфигурации («3 решения сделаны локально. [Закрепить]»); лаунчер может
  открыть nix_cm на нужном месте. В обратную сторону — ничего само: ни
  программа, ни лаунчер не пишут в конфигурацию владельца, у программы зоны
  нет даже косвенного пути к ней.

Сегодня правило грубее — объявленное в Nix просто побеждает; уточнение
(Nix-потолок, местное внутри) — небольшая переделка чтения настроек.

## 7. Перетаскивание и буфер обмена между контейнерами

**Текст и ссылки** перетаскиваются между любыми зонами и хостом уже сейчас:
Wayland передаёт данные через композитор, посредник (`wl_proxy`) этот протокол
пропускает. Буфер обмена — только окну в фокусе: чтение в фоне
(`data-control`) зонам закрыто.

**Файлы.** При общем доме (программы зон без песочницы) перетаскивается путь,
и он работает. В песочницу — только через портал FileTransfer, как во Flatpak
(GTK4, Qt6: получатель видит только брошенный файл через портал документов).
Старые программы передают просто путь, которого в чужой песочнице нет.

**Цель: перетаскивание — это разрешение.** Бросить файл в окно — явное
действие человека, как выбор файла в портале. Посредник видит, что в окно
песочницы бросают `text/uri-list` с файлами, регистрирует их в портале
документов и подменяет пути на видимые получателю: контейнер получает ровно
брошенные файлы — ни папки, ни соседей. Из песочницы наружу — наоборот: путь
в её доме переводится в путь хранилища контейнера на хосте (§2).

## 8. Переход со старого устройства

Помощник (в лаунчере и командой) сначала показывает, что будет сделано, и
переносит по кнопке; сам ничего не удаляет — старое остаётся до отдельной
команды:

- **слои у зон** (`isolate overlay`, прежнее умолчание: у каждой зоны свой
  слой над `~/.config` и остальным) — в контейнеры с именем зоны и той же
  сетью; накопленное программами сохраняется;
- **закрепления** «программа → сеть» (`cellward pins`) — в «программа →
  контейнер»;
- **песочницы и именованные контейнеры** остаются как есть — они уже
  контейнеры; сливаются, если нужно, `cellward container merge` (совпавшее —
  у целевого, версии из второго — рядом, чужие корневые сертификаты — только с
  согласием).

Зоны (сети) объединять не нужно: в этой модели зона — выход наружу, которым
пользуются контейнеры; одинаковые VPN узнаются уже сейчас (системный уровень:
«это та же зона», второй туннель не поднимается).

## 9. Удобство

- **Предупреждение при переносе между зонами** (перетаскивание, вставка из
  буфера) — отключаемое: «Вы переносите из зоны Работа в зону Банк».
  Всегда / только между разными сетями / никогда; у контейнера можно
  требовать подтверждения всегда. Зоны источника и получателя знает
  посредник Wayland.
- **Буфер обмена.** Посредник помечает данные зоной, которая их положила
  (служебный MIME-тип): менеджер буфера на хосте (форк CopyQ или сценарий к
  нему) показывает историю с пометкой «из зоны Работа»; вставка в другую зону
  — то же предупреждение; у строгого контейнера («Банк») — буфер только внутри
  него: чужое вставляется и своё уходит наружу только с подтверждением.
- **Очистить контейнер** — одной кнопкой с подтверждением: стереть хранилище;
  отдельно — сбросить разрешения. (Кусочки есть: `container rm`,
  `trust reset`.)
- **Дубликат контейнера** — копией (reflink, где файловая система умеет), без
  наследования: ветвление overlayfs с родителем тихо меняло бы потомков при
  изменении родителя. Для общих настроек — шаблоны контейнеров в Nix: новый
  контейнер создаётся из шаблона и дальше живёт сам.
- **Одна точка «спросить человека»** для всех вопросов (микрофон,
  перетаскивание, брокер): сегодня kdialog и уведомления, завтра — ещё и
  приложение на телефоне, без переделки остального. Свой диалог (режим
  `vpn-zone-window`) вместо kdialog: по умолчанию «Отказать», Enter и Escape
  — отказ, кнопки «разрешить» оживают через секунду (как у установки
  дополнений в Firefox), сроки из §3е — в том же окне. Пока вопрос задаёт
  kdialog, у которого по умолчанию первая кнопка — «разрешить», «да»
  быстрее 1,5 с считается случайной клавишей (LEAK-MODEL §22).
- **Запуск:** программа уже запущена в своём контейнере — фокус на её окно, а
  не второй экземпляр (реестр запусков знает, IPC niri или sway переключает);
  «ещё одно окно» и «в другом контейнере» — явным пунктом меню; ярлык меню
  системы — в контейнер программы, иначе в новый без сети.

## 10. Порядок работ

1. Микрофон: тишина до разрешения с уведомлением и переключением на ходу
   (поверх ограниченного PipeWire и политики WirePlumber — в работе).
2. Незнакомая программа — в свой контейнер без сети, без вопроса, с
   уведомлением.
3. Камера: чёрный кадр так же (свой видеоисточник PipeWire), затем портал
   Camera.
   Экран (§3д): выключатель `screencast` на зону (сделано), метка «идёт
   трансляция» с кнопкой «остановить», снимок только по вопросу.
   Сроки (§3е): «один раз / пока открыт контейнер / на время / всегда» для
   микрофона, камеры и экрана — тем же механизмом, что у каталогов.
4. Хранилища контейнеров на хосте (`~/Контейнеры/`).
5. Лаунчер от контейнеров (`vpn-zone-window`).
6. Рамки Nix и местные решения, «закрепить» в nix_cm.
7. Поведение до разрешения по ресурсам и контейнерам; модули-имитаторы в
   своих зонах.
8. Интерфейс для адаптированных программ.
9. Перетаскивание файлов как разрешение (посредник и портал документов).
10. Помощник перехода со старого устройства.
11. Срез systemd на контейнер: ресурсы (ROADMAP) и сетевой фильтр (§3а) —
    открыто / список разрешённого / спрашивать.
12. Маршрут по назначению (§3б): страна, имена, локальная сеть → выход;
    затем zapret как вид выхода (§3в).
13. Выходы как граф (§3г): цепочка «VPN через VPN» на механизме «зона через
    зону», проверка схемы в `doctor`, блок-схема в окне; прокси как выход —
    отдельно, с адаптером.
14. Удобство (§9): предупреждение о переносе, метки и изоляция буфера,
    очистка и дубликат контейнера, фокус вместо второго экземпляра, одна
    точка вопросов.

Вне этого документа: приложение на телефоне для подтверждений — отдельная
часть; подтверждение sudo и входа по отпечатку — это PAM, не cellward.

## 11. Перестройка: разрешения с зон — на контейнеры

Решение владельца 2026-09-26: основа всего — контейнер, зона — только
транспорт. До этого разрешения появлялись на зонах (микрофон, экран, камера,
X-сервер, герметичность, Nix-демон, запись в файлы хоста, менеджер звука),
потому что места проверки — фильтр звука, фильтр шины, держатель — были
зонными. Это расходилось с §1 и разворачивается здесь.

### 11.1 Что остаётся у зоны

Туннель и аплинк, DNS, замок (`lock`), наблюдение за туннелем, выход хоста
(системный уровень). Больше ничего — цвет рамки тоже у контейнера (§1),
владелец 2026-09-26.

### 11.2 Что переезжает на контейнер

| сейчас у зоны | у контейнера | где проверяется |
|---|---|---|
| `microphone` | `microphone` yes/no/ask | фильтр звука и PipeWire: свой сокет на контейнер (§11.4) |
| `screencast` | `screencast` yes/no/ask | фильтр шины: свой на запуск контейнера |
| `camera` | `camera` | устройства — в пространство запуска контейнера (**сделано**) |
| `x11` (`zoneX11`) | `x11`: да, нет или как у сети (**сделано**, 2026-09-28: «нет» контейнера отказывается и от X-сервера зоны; было «контейнера ИЛИ зоны») | `x11-run` |
| `hermetic` | `hermetic` (по умолчанию — как у сети) | экземпляр контейнера поднимается с ней (**сделано**, 2026-09-28) |
| `nix-daemon` | `nix_daemon` | то же (**сделано**) |
| `audio-manager` | `audio_manager` | то же (**сделано**) |
| `host-files` | `host_files_writable` — пока; дальше это решает дом (§11.3) | то же (**сделано**) |
| цвет рамки (`frame.colors`) | `frame_color` | посредник Wayland запуска: цвет — по контейнеру, подпись «сеть · контейнер» остаётся |

**Герметичность, Nix-демон, файлы хоста, менеджер звука — у контейнера
(этап 5 контейнерного дизайна, 2026-09-28).** Экземпляр контейнера — одно
пространство на контейнер, и его покрытия и помощники делаются при подъёме
(`hermetic::start_settings_for`): поэтому эти четыре — настройка
экземпляра, а не запуска, и действуют со следующего его подъёма
(`instances[].restart_needed`). В Nix —
`containers.<имя>.permissions.{hermetic, nixDaemon, hostFilesWritable,
audioManager}` (`null` — как у сети), локально — `cellward container set
<к> hermetic|nix-daemon|audio-manager default|on|off` и `host-files
default|read-only|writable`; `status --json` — `containers[].hermetic`,
`nix_daemon`, `host_files_writable`, `audio_manager` (свои, `null` — нет
своего). Что важнее — порядок камеры (`hermetic::for_container`): слово Nix
для контейнера, затем Nix для его сети (местное слово не перебивает
объявленное, чтобы открыть больше, — но перебивает, чтобы закрыть: ревью
2026-09-28, местное `nix-daemon off` при сети в `nixDaemon` молча не
действовало), затем местное слово контейнера, затем настройка сети.
Непонятное слово или нечитаемый файл — безопасное значение: герметичен, без
демона, файлы хоста только для чтения, без сырого PipeWire. Основной дом
берёт настройки сети. Разовые запуски (разовый контейнер, временный слой
над домом) и программа, чей контейнер не опознан, — безопасные значения,
что бы ни говорила сеть (ревью 2026-09-28: брали настройки сети, и разовый
запуск в сеть, дающую своим контейнерам Nix-демон или запись файлов хоста,
получал их тоже), — как у микрофона неопознанному «да» становится
«спросить». Опции зон
(`hermetic.exceptions`, `nixDaemon`, `hostFilesWritable`, `audioManager`,
`zoneX11`) работают как значения по умолчанию для контейнеров без своего —
с предупреждением при сборке; `hermetic.default` остаётся общим умолчанием.

**Nix-демон и `trusted-users` — это root** (ревью 2026-09-28). Если
пользователь (или его группа, `@wheel` тоже) в `trusted-users` nix.conf
хоста, демон слушается его во всём, что задаёт сборку: выключить песочницу
сборки, подставить свой кэш, хук после сборки, — и программа контейнера с
`nix_daemon` может то же, что root хоста, а не только качать мимо туннеля.
`doctor` читает `/etc/nix/nix.conf` так, как его читает Nix (`include`,
`!include`, `extra-trusted-users`), и предупреждает (`nix-trusted`), если у
запущенного экземпляра, у контейнера своим словом или у сети Nix-демон, а
пользователь — доверенный. Выход: убрать пользователя и его группы из
`trusted-users` (достаточно `allowed-users`) — или выключить Nix-демон
(`cellward container set <к> nix-daemon off`, `cellward nix-daemon <зона>
off`). THREAT-MODEL H9.

### 11.3 Виды дома

- **свой дом** (стандарт, §2): пустой дом контейнера плюс выданные папки
  (`container grant`, на срок и на ходу);
- **слой над домом**: весь настоящий дом виден, запись — в слой контейнера;
  плюс **общие пути** — то, что пишется в настоящий дом насквозь. Слой
  накрывает весь дом, а не только `.config` и соседей, как профили сейчас:
  иначе `.bashrc`, автозапуск и проекты писались бы мимо слоя (механизм —
  из ветки `feat/home-layer`: возврат путей поверх через дескриптор
  настоящего дома, ссылки из слоя не уводят монтирование, диски внутри дома
  возвращаются);
- **«Основной»** — настоящий дом целиком. Явный выбор, окно запуска помечает
  его опасным. Для доверенных инструментов: файловый менеджер, свой
  терминал.

Нынешние контейнеры-профили (слои над частью дома) переходят в слой над всем
домом, накопленное сохраняется.

### 11.4 Разные правила в одной сети

Каждый запуск контейнера уже в своём пространстве монтирования
(`profile-run`). Помощники зоны — фильтр звука, контекст PipeWire, фильтр
шины — выдают каждому контейнеру **свой сокет**, и запуск кладёт его на
стандартное место (`/run/user/<uid>/pulse/native`, `pipewire-0`, `bus`).
Правило читается по контейнеру, которому выдан сокет, а не по тому, что
скажет программа. Два контейнера в одной сети получают разные разрешения.

### 11.5 «Основной» и файловый менеджер

Файловый менеджер (Dolphin) — в «Основном» и по умолчанию без сети: это
инструмент человека для настоящих файлов и для переноса между контейнерами.
Хранилища контейнеров видны ему в `~/Контейнеры/<имя>/` (§2). Предпросмотр и
миниатюры там **выключены**: разбирая чужой файл (картинку, видео, PDF) с
правами на весь настоящий дом, библиотека миниатюр — прямой выход наружу для
подложенного файла.

### 11.6 Переход

- Настройки зон становятся начальными значениями контейнеров, которые в этой
  сети работают (у кого не задано своё); цвет зоны — цветом её контейнеров,
  у контейнера без своего цвета и без зоны — цвет из имени. Старые опции Nix работают ещё
  какое-то время — с предупреждением (с 2026-09-28: `hermetic.exceptions`,
  `nixDaemon`, `hostFilesWritable`, `audioManager`, `zoneX11`).
- Программы, которые сейчас запускаются в «Основном», там и остаются до
  явного переназначения; окно запуска это показывает.
- stillconf: в карточке cellward главное — список контейнеров (сеть, дом,
  общие пути, разрешения); раздел сетей — только сетевое.

### 11.7 Одно имя — один контейнер

Аудит 2026-09-26 нашёл, что в коде контейнер собран из двух осей: `work`
(слой) и `sb:work` (свой дом) — два разных контейнера с разными каталогами,
настройками и командами, а «Основной» — не контейнер вовсе. Устройство:

- **Имя одно, вид дома — свойство:** `home = private | layer | main` (в Nix
  и в `container.conf`; `overlay` читается как `layer`). Смена вида дома не
  создаёт другого контейнера: сеть, программы, папки и сертификаты остаются.
  Данные прежнего вида откладываются рядом (`home.<вид>`) и возвращаются при
  обратной смене — ничего не стирается.
- **Одно место данных и одно — настроек:** данные —
  `~/.local/state/vpn-profiles/<имя>/` (у дома `main` данных нет; имя
  каталога историческое — его закрывают все зоны, и запущенные до перехода
  тоже, а новый каталог они бы не закрыли), настройки —
  `~/.config/vpn-zones/containers/<имя>/` (`container.conf`: вид дома, сеть,
  программы, X-сервер, потом — разрешения §11.2 и цвет; `paths`, `perms`,
  `trust/`), объявленное в Nix —
  `declared/containers/<имя>.conf`. Программы контейнера — строки `app` в его
  настройках, а не файлы по программе в состоянии.
- **«Основной» — вид дома.** Встроенный контейнер `main` — настоящий дом,
  сеть спрашивается при запуске; именованных контейнеров с домом `main`
  сколько угодно («Файлы» без сети, «Терминал» через VPN — у каждого свои
  разрешения и цвет). Одна сеть за раз (I2) у дома `main` не проверяется:
  личность настоящего дома одна на все сети, разделять нечего — это цена
  «Основного», и окно запуска её называет. Своих сертификатов у дома `main`
  нет: они легли бы в настоящий дом.
- **Разовые запуски** (`--fs-sandbox`, `--tmp-profile`; в окне запуска —
  «Разовый контейнер» с пустым домом и «Временный слой над домом») — не
  контейнеры: без имени и без памяти. Ответы о папках разового контейнера не
  запоминаются по программе.
- **Команда одна — `container`;** `profile` и `sandbox` — её псевдонимы с
  видом дома по умолчанию `layer` и `private`. `isolate` и `reset-profile`
  убираются: слоёв у зон больше нет, они ничего не делают.
- **Переход — один раз, на хосте:** каталоги из `vpn-sandboxes/`
  переезжают в `vpn-profiles/` целиком (переименование на том же диске;
  запущенные программы его не замечают), `sb:<имя>` в памяти окна, в Nix
  (`defaults.container`) и в учёте запусков читается как `<имя>`. Если есть и слой `work`, и свой дом `sb:work`, второй получает
  имя `work-sb`; отчёт перехода это называет. Имя, которое не может быть
  именем (начинается с `-` или `.`), не переносится и тоже называется.
- **`status --json`:** `selector` контейнера совпадает с `name`; у `home`
  новое значение `main`, слой по-прежнему `overlay` — версия схемы 1 не
  меняется.

### 11.8 Сеть — у контейнера

- **Закрепление сети за программой** (`.pinned/<программа>`) уходит. При
  переходе оно становится сетью контейнера программы, если у того сети ещё
  нет и его программы не спорят; программы «Основного» с закреплённой сетью
  переходят в контейнер `main-<сеть>` с домом `main` — запускаются так же,
  но теперь у них есть место для разрешений. Где программы спорят, контейнер
  остаётся «спрашивать», и отчёт это называет.
- **`ask` — «ещё не выбрано»:** сеть спрашивается при запуске, и «Всегда»
  привязывает к ней контейнер. Без «Всегда» ничего не привязывается:
  привязка — отдельное действие, а не побочный эффект одного запуска (I1).
  Общий контейнер по умолчанию (`default-profile = <имя>`) из одного запуска
  не привязывается вовсе — иначе туда без вопроса пошла бы каждая новая
  программа; его сеть меняется в его настройках. Удаление зоны снимает
  местные привязки к ней.
- **Окно запуска выбирает контейнер,** сеть показана как его сеть; сменить её
  — отдельное действие «Сеть контейнера…» — в окне и в меню окна программы.
- **Один запуск — один контейнер:** сочетание «слой + свой дом» больше не
  собирается (`run` отказывает), учёт запусков — `.running/<контейнер>/`.
  Проверка «уже запущен в другой сети» идёт по контейнеру.
- **Смена сети работающего контейнера — на ходу** (этап 4, 2026-09-27;
  LEAK-MODEL §29): `cellward container set <к> network <сеть>` при
  работающих программах меняет выход его экземпляра, не перезапуская их —
  соединения рвутся, сокеты прежней сети немеют за стеной эпох, DNS следует;
  перед сменой человеку говорится, что сайты свяжут прежнюю сеть с новой
  (cookies, входы). Смена пишет новую сеть в настройку контейнера и переносит
  его записи запусков: и окно, и «уже запущен в другой сети» видят его там,
  где он теперь. Только с хоста и только по слову человека; чего на ходу не
  сменить — отказ с `--restart` (закрыть и открыть заново).

### 11.9 Где проверяется: запуск контейнера, а не зона

- **Брокер:** источник — контейнер, а не текст запроса и не одна зона; без
  вопроса — только тот же контейнер (в той же зоне); «всегда» и журнал — по
  контейнеру (`зона/контейнер`); ссылка из контейнера открывается от его
  имени, а не в «Основном» зоны. **Сделано (2026-09-26)**, ссылки от имени
  контейнера — тоже (§11.13): контейнер источника узнаётся без отдельного
  сокета на запуск — по запуску, от которого программа происходит
  (запускающий процесс из учёта запусков, с временем старта, и цепочка
  родителей, прочитанная с удержанием каждого), а программа без контейнера — по собственному пространству монтирования
  зоны. Демон, ушедший из дерева своего запуска, не опознаётся и спрашивается.
- **Контейнер «напрямую»** (`unconfined`): помощники — фильтры звука,
  PipeWire и шины, X-сервер, рамка — запускаются на запуск контейнера, для
  него — в сетевом пространстве хоста. Пока их нет, окно запуска говорит, что
  у контейнера «напрямую» разрешения §11.2 не проверяются.
- **Портал:** имя программы у портала — `cellward.c.<контейнер>` (ярлык на
  контейнер, тот же id во `FLATPAK_ID`); решения о трансляции, камере,
  уведомлениях — по контейнеру, диалог портала называет контейнер.
- **Замок зоны** требует герметичности у всех её контейнеров; `status` и
  `doctor` называют контейнер, который замок не держит. **Сделано**
  (2026-09-28): запуск в запертую зону, смена на ходу в неё и подключение
  экземпляра к ней отказывают экземпляру, поднятому (или который поднялся
  бы) не герметичным; `cellward lock` называет такие контейнеры —
  работающие в ней и привязанные к ней, `status --json` —
  `networks[].lock_not_held_by`, `doctor` — проверка `lock` зоны (работающий
  не герметичный — нарушение, привязанный — предупреждение).
- **`doctor`** пробует каждый запущенный контейнер в его пространстве, а не
  зону.
- **Жетоны `fs-perms`** (загрузки, документы, изображения, дом, X-сервер)
  становятся выданными папками контейнера (`paths`, со сроком и отзывом);
  жетон «дом» — это дом `main`, X-сервер — одно поле `x11`.
  `wayland-allow` и `wayland-no-proxy` — поля контейнера, а не имени
  программы.

### 11.10 Как помощники узнают контейнер

Разбор помощников 2026-09-26: фильтр звука и фильтр шины не знают клиента —
правило у них одно на зону; PipeWire принимает клиентов сам, и помощник
только выдаёт зоне сокет с её именем. Свой сокет на каждый запуск
(§11.4) — не единственный путь, и не лучший: пространство монтирования
контейнера — копия, снятая при запуске, туда ничего не добавить потом, а
контейнер основного дома своего пространства не имеет вовсе.

- **Один способ для всех — как у брокера** (общий модуль `origin`: им
  пользуются брокер и фильтр звука): номер клиента от ядра (`SO_PEERPIDFD`), цепочка его
  родителей, прочитанная с удержанием каждого, и ближайший запуск из учёта
  запусков с тем же временем старта — это и есть контейнер. Запуск
  основного профиля — «основной»; ничего не найдено — «не опознан». Учёт
  запусков и `/proc` видны и хосту, и зоне (только для чтения).
- **Ближайший запуск решает**, чей бы он ни был: разовый контейнер,
  запущенный из программы контейнера, — не этот контейнер.
- **Ушедший из дерева запуска** (демон после двойного `fork`, программа, чей
  запуск закончился) — «не опознан», если он не в собственном пространстве
  монтирования зоны. Там — только программы зоны без контейнера: у каждого
  запуска контейнера своё пространство, и у контейнера основного дома тоже
  (пустое, `launch::Entry::own_mounts`), а покинуть его без прав нельзя.
  Пространство процесса запуска для этого не годится: запуск оборачивает
  `wl-sandbox`, а он остаётся на хосте.
- **Номер, на который претендуют два запуска** (заметки о старте — на
  номер, а не на запись), — ничей.
- **Не опознанный** (разовый контейнер, имя удалённого контейнера, ушедший
  из запуска) — правило зоны, но «да» становится «спросить», и «всегда» не
  предлагается: самое строгое из того, что о нём известно.
- **Фильтр звука** (на хосте): контейнер — на каждое подключение, один
  раз, пока подключившийся точно жив; микрофон — `microphone = yes|no|ask`
  в настройках контейнера (`cellward container set <к> microphone`, Nix —
  `containers.<к>.permissions.microphone`). Какое слово решает: Nix
  контейнера → Nix зоны → местное контейнера → местное зоны → `ask`.
  Местное не перебивает объявленное в Nix, чтобы открыть больше: «нет»
  зоны из Nix контейнер локально не отменит. Чтобы открыть меньше —
  перебивает (ревью 2026-09-28): местное «нет» при «да» или «спросить»
  зоны из Nix, «спросить» при «да» — действуют; Nix — рамка, контейнер в
  ней просит меньше. То же у трансляции экрана и камеры. Вопрос называет контейнер, «всегда» пишет
  `microphone = yes` в его настройки (не в удалённый за время вопроса);
  программе без контейнера «всегда» — по-прежнему зоне; не опознанной —
  не предлагается. Замок вопросов и пауза после отказа — прежние, на зону:
  один диалог на экране. **Сделано** (путь pulse).
- **Чего это не держит.** Контейнеры одной зоны делят её пространство
  пользователей, `/tmp` и абстрактные сокеты: программа одного может
  попросить программу другого подключиться за неё. Между контейнерами
  одной зоны микрофон — настройка, а не стена; стена — между зонами и
  между контейнером и хостом. Своё `/tmp` и скрытые процессы у запуска —
  в плане (п. 8 §11.11).
- **Offline — стена, не настройка (2026-09-27, этап 1 контейнерного
  дизайна).** Запуск с сетью `offline` идёт в экземпляр своего контейнера
  (CONTAINERS §3.6, LEAK-MODEL §28): свои пространства пользователя, сети,
  IPC и точек монтирования, своя `/tmp`, свои помощники. Помощникам
  экземпляра не нужно узнавать контейнер по запуску: экземпляр и есть
  контейнер — фильтр звука, фильтр шины и контекст PipeWire получают его
  при старте (`--container`), а подключившегося проверяют по пространству
  пользователя (`--userns`, `crate::place`); брокер узнаёт экземпляр так же,
  по ядру, и слово фильтра шины о контейнере для него не читает. С
  этапа 2 так же идёт и запуск в зону, а с этапа 3 (2026-09-27) у
  экземпляра и своё пространство pid: программа контейнера не видит
  процессов хоста и других контейнеров (THREAT-MODEL X4, LEAK-MODEL §28), а
  брошенного программой демона подбирает `profile-run` её запуска, не pid 1
  экземпляра, — он остаётся под надзирателем запуска (WINDOW-FRAME,
  «Жизнь»). Всё сказанное выше про контейнеры одной зоны остаётся для
  программ, которые прошлая сборка запустила в пространства самой зоны; с
  этапа 5 (2026-09-28) туда не запускается ничего, а помощники зоны знают
  только её собственное пространство монтирования (LEAK-MODEL §30).
- **Фильтр шины зоны** (в зоне, без прав): контейнер — на каждое
  подключение, тем же `origin`; своё пространство монтирования зоны — его
  собственное (`/proc/self/ns/mnt`: в `/proc` держателя с правами ему не
  заглянуть), учёт запусков и настройки — через дескрипторы, взятые до того,
  как зона их закроет (и каталог данных контейнеров тоже). Трансляция экрана
  — `screencast = yes|no|ask` контейнера по правилу микрофона
  (`microphone::by_container`); отказ называет контейнер. **Сделано.** Имя у
  портала было зоны: выбор, запомненный под ним, был бы выбором всех
  контейнеров зоны, поэтому «да» контейнера было «спрашивать». Теперь своё
  имя `cellward.c.<контейнер>` — **сделано** (`desktop::container_app_id`,
  ярлык для портала пишет sync): фильтр регистрирует под ним соединения
  контейнера, где ярлык есть, и «да» контейнера хранит свой выбор; без
  ярлыка — имя зоны, как раньше, и «да» — «спрашивать». Программа
  песочницы приходит через фильтр песочницы, а тот происходит от запуска
  песочницы — он и называет контейнер.
- **PipeWire — по клиенту. Сделано.** Помощник видит каждого клиента демона
  в его реестре: `pipewire.sec.pid` (демон берёт его у ядра) и
  `object.serial` (у другого клиента такого не бывает). Клиент, чей процесс
  в сетевом пространстве зоны, — её; чей он, узнаётся один раз, по запуску
  (`origin`, как у фильтра звука). Ключ `vpn-zones.microphone.client.<serial>`
  = yes|no, метка `vpn-zones.microphone-by-client.<зона>` = serial
  собственного клиента помощника: пока этот клиент есть, политика решает
  только по ключу клиента и придерживает нового клиента, пока ключ не
  придёт, — просит его (`vpn-zones.microphone.pending.<serial>` = зона), и
  помощник отвечает на каждую просьбу своей зоны, клиенту, чей контейнер
  не узнать, — настройкой неизвестного. Часов нет (владелец, 2026-09-26: на
  медленной машине ожидание дольше, решение — то же): клиента отпускает его
  ключ, а ушёл клиент помощника — ключ зоны. Метка `yes` (помощник прежней
  версии) не отслеживается: решает ключ зоны. Ключ зоны
  (самое строгое из зоны и запущенных в ней контейнеров) остаётся для
  политики прежней версии. Чего это не держит: pid — слово демона, а не
  pidfd, и клиента демон регистрирует при его первых свойствах, когда
  захочет программа; подключившись из потомка, который потом вышел,
  программа в принципе может дождаться, пока его номер займёт процесс
  другого контейнера той же зоны (у фильтра звука pidfd от ядра, такой щели
  нет) — ещё одно «настройка, не стена» между контейнерами одной зоны.
  Ключи клиентов, живых в момент, когда помощник погиб, остаются в
  метаданных до перезапуска WirePlumber — безвредно: `object.serial` не
  повторяется.
- **Цвет рамки** — контейнера (без своего — зоны, потом из имени):
  `wl-sandbox` получает его при запуске, на хосте.
- **Покрытия монтирования** (камера, Nix-демон, запись в файлы хоста,
  герметичность, менеджер звука, X-сервер): у запуска контейнера — всегда
  своё пространство монтирования, и основного дома тоже; `profile-run`
  накладывает покрытие по настройке контейнера или снимает покрытие зоны
  (оба пространства в пространстве пользователей зоны — проверить на ядре
  до обещаний). Свой `/tmp/.X11-unix` у каждого запуска с X-сервером —
  **сделано** (2026-09-27, `profile-run --own-x11`, HERMETICITY §7 A): сокет
  спутника только у этого запуска, абстрактного сокета нет; до того сокеты
  спутников были видны всем контейнерам зоны.

### 11.12 Устройства контейнера (владелец, 2026-09-26)

У зоны свой `/dev` (`zone::own_dev`, LEAK-MODEL §19) — tmpfs, в котором
есть только основа и GPU, и ничего больше. Это запрет по умолчанию
(владелец, 2026-09-26): список того, что закрывать, пропускает то, о чём
никто не подумал, — так нашлись открытыми всем `kvm`, `vhost-net`,
`vhost-vsock`, `net/tun`, `vfio/vfio`, `kmsg`, — а закрывать узлы по одному
на общем devtmpfs значит оставить открытым подключённое позже там, где
программа сделала своё пространство имён (`unshare` делает его частным, и
крышки зоны туда не доходят). На tmpfs зоны подключённое позже не
появляется нигде. В `/dev` зоны привязаны из devtmpfs только `null`,
`zero`, `full`, `random`, `urandom`, `tty`, `fuse` (AppImage монтирует
себя), `ntsync` (блокировки Wine и Proton, ничего общего) и GPU: `dri/*` и
у NVIDIA `nvidia<N>`, `nvidiactl`, `nvidia-modeset`, `nvidia-uvm`,
`nvidia-uvm-tools` — без них ничего не рисуется (узел GPU, появившийся
позже, наблюдатель добавляет); свои терминалы (`pts`, `ptmx` —
отдельный экземпляр devpts: терминалы хоста зоне не видны); ссылки
devtmpfs (`fd`, `stdin`…) и точки монтирования на нём (`shm`,
`hugepages`) — как были; `mqueue` — свой, из IPC-пространства зоны
(2026-09-27: хостовый давал очереди хоста). Сам devtmpfs зона держит в
`/dev/.cellward/devtmpfs`, в каталоге `0700` своего root: ни программа
зоны, ни root пространства пользователей, которое она сделает, туда не
войдут. Имена устройств нужны только выдаче: ошибка в них — «не
выдалось», а не «утекло». Программа, запущенная в зону из терминала хоста,
работает с ним по-прежнему, но имени у него не узнает (`tty`: «not a tty» —
как во Flatpak). Программе, которой нужен редкий узел
(`/dev/kfd` для вычислений на AMD, `accel/*`, `dma_heap/*`, `udmabuf`),
его пока не выдать: нужен новый набор или место в основе. Так же пока нет
камер, которые снимают через libcamera с программной обработкой (IPU6):
им нужны `dma_heap`/`udmabuf`, а настройка камеры их не открывает.
В контейнер устройство идёт только по выбору — как USB в
виртуалку, но без отнятия у хоста.

- **Что выдаётся** — `devices` контейнера, список (Nix
  `containers.<к>.permissions.devices`, локально `cellward container devices
  <к> add|rm …`, в `status` — `containers[].devices` с источником у каждого):
  - наборы одной кнопкой: `games` — геймпады (узлы ввода с
    `ID_INPUT_JOYSTICK`, физические, не клавиатура и не мышь, и их `hidraw`);
    `security-keys` — ключи FIDO (`hidraw` с `ID_SECURITY_TOKEN`); `phone` —
    телефоны (узлы `bus/usb` с интерфейсом adb или MTP/PTP); `serial` —
    `ttyUSB*`, `ttyACM*`; `vm` — виртуальные машины: `kvm`, `vhost-net`,
    `vhost-vsock` и `net/tun` (сеть машины через свой tap);
  - одно устройство: `usb:<vendor>:<product>[:<serial>]` — все его узлы из
    тех, что выдаются (`hidraw`, ввод, `bus/usb`, `ttyUSB`/`ttyACM`; не
    `hiddev`, `lp`, диски, камеры);
    переживает переподключение и другой номер `/dev/…`;
  - все устройства: `all` (2026-09-29, у «без изоляции» — всегда).
    `profile-run --all-devices` привязывает devtmpfs хоста целиком поверх
    `/dev` запуска: подключённое позже тоже там, ушедшее уходит само.
    Своё у `/dev` зоны — терминалы (`pts`), `shm`, `mqueue`, `hugepages` —
    возвращается поверх, так что терминалы хоста не видны и тут. Для
    песочницы со своим домом (`fs-sandbox`) `all` пока не действует.
- **Как**: при запуске хост перечисляет узлы и сверяет их с выданным (по
  базе udev, `/run/udev/data`); `profile-run --device
  <путь>=<maj:min>:<vid:pid>[:<серийный>]` в своём пространстве запуска
  сверяет номер, производителя, модель и серийный номер ещё раз (номер
  могло занять другое устройство между перечислением и запуском) и
  привязывает узел из devtmpfs зоны на пустую заглушку в `/dev` зоны (её
  root-а, режим `0`; другим программам зоны она видна пустым файлом, не
  устройством). Когда устройство уходит, наблюдатель зоны удаляет заглушку
  — и ядро снимает все привязки на ней, во всех пространствах имён, и в
  сделанных программами тоже. Программе без контейнера устройств нет.
- **Песочница** (свой дом) получает узлы привязкой (`fs-sandbox --device`), а
  привязка держит inode устройства — и открыла бы то устройство, которое
  займёт его номер следующим (ядро даёт наименьший свободный: клавиатура,
  воткнутая после ключа, получит его `hidraw`). Поэтому держатель зоны,
  увидев, что устройство ушло, заходит в пространство монтирования каждой
  программы зоны, кроме своего, снимает там привязку и кладёт `/dev/null` на
  её место (`device_guard::revoke_everywhere`; поверх привязки удалённого
  узла ядро монтировать не даёт — GOTCHAS §6).
- **Ссылка, оставшаяся у программы** — дескриптор на узел (и `O_PATH`,
  переоткрываемый через `/proc/self/fd`), привязка, сделанная ею в своём
  пространстве имён, — тоже открыла бы следующее устройство под этим номером.
  Держатель помнит каждый узел, каким он был (устройство, inode), и когда
  номер ушедшего получает новое устройство, убивает каждую программу зоны,
  что ещё держит старый узел, — если это не то же самое устройство
  (`device_guard::identity`: слово ядра в sysfs — USB-устройство с
  производителем, моделью и серийным номером, интерфейс, HID, устройство
  ввода с именем и тем, что оно сообщает; геймпад, вернувшийся после
  разряда, — тот же, клавиатура на номере ключа — нет, неизвестное — не то
  же). Программы зоны — процессы её пространства пользователей и вложенных,
  в какой бы сети они ни были. Ни одно решение здесь не зависит от часов:
  заход в пространство программы работник запускает и не ждёт — его ждёт
  только поток, пишущий итог в журнал, сколько бы он ни шёл (медленная
  машина, свап, FUSE поверх `/dev`, подвешенный программой нарочно);
  прерывает его лишь следующий заход за тот же узел. Наблюдатель от него
  не зависит, проверка номера идёт без очереди за
  заходами и решает по тому, что есть в этот миг: привязка, которую ещё не
  сняли, в этот миг открывает новое устройство — и программы её
  пространства уходят.
  Не держит: пока новое устройство не появилось в `/dev` (миллисекунды),
  держащая программа уже может его открыть — и её убьют через мгновение;
  дескриптор, переданный из зоны программе другой зоны.
- **Подключённое позже** закрыто и у разрешённого запуска — перезапустить
  программу. Открывать новое устройство в разрешённых запусках — дальше.
- **Чего это не держит**: пока разрешённый запуск работает, другая программа
  той же зоны вне песочницы достаёт выданное устройство через
  `/proc/<pid>/root/dev/…` (как с камерой; закроет скрытие процессов у
  запуска). `serial`: узлы `ttyUSB`/`ttyACM` обычно группы `dialout`, которую
  зона снимает, — нужен ACL сеанса (`uaccess`) на это устройство, иначе
  программа получит отказ. **Опасно**: `serial` и `usb:` для платы, которую
  программа может перепрошить (Arduino и подобные): плата перечислится
  заново клавиатурой и напечатает в сеанс хоста — выдавать только доверенному
  контейнеру. **Сеть мимо туннеля** (аудит 2026-09-27): `phone` отдаёт весь
  USB-узел телефона — `adb shell` пользуется сетью телефона, а отсоединить
  драйвер хоста от USB-модема телефона и вести его самому ядро позволяет без
  прав; так же `serial`/`usb:` для платы с Wi-Fi (ESP32) или LTE-модема.
  Такой контейнер выходит в сеть не через туннель своей зоны.
- **Игры** (дальше): `/dev/ntsync`; виртуальный геймпад Steam Input — через
  свой `uinput` (служба с root, CUSE), только с кнопками и осями геймпада и
  видимый лишь в своём контейнере; клавиатура и мышь Steam Input — только в
  окна своего контейнера, через `wl-sandbox`. Сырой `uinput` — отдельная
  опасная отметка, не в наборе.

### 11.13 Ссылки от имени контейнера (владелец, 2026-09-26)

Ссылку, которую открывает программа герметичной зоны (или песочницы), фильтр
шины отдаёт брокеру на хосте (`VZL1`, `rust/src/links.rs`,
`broker::handle_link`), а не `xdg-open` в зоне. Два выбора, у каждого свой
хозяин:

- **Программа — дело дистрибутива.** Окно выбора бэкенда портала
  (`org.freedesktop.impl.portal.AppChooser`) — то, которое конфигурация
  порталов назначает выбору программы (`AppChooser=kde` в
  `<desktop>-portals.conf`, иначе `default`; GNOME, KDE, GTK по очереди, у
  кого окна нет — следующий, нет ни у кого — меню kdialog). Зовётся
  реализация, а не сам портал: она отвечает выбором и ничего не запускает.
  Список программ передаём сами — ярлыки с `x-scheme-handler/<схема>`,
  умолчание дистрибутива (`mimeapps.list`) первым; «Показать все» у KDE —
  запасной выход, и выбранное там тоже принимается, если такой ярлык есть и
  он берёт ссылку. Одна программа на такие ссылки — окна нет, как на
  телефоне.
- **Контейнер и сеть — дело CellWard.** Окно запуска, как для любого запуска,
  о котором просит зона: спросившая зона в нём, Enter — только в ней.
  Ярлык, который CellWard не перехватывает (симлинк пользователя или
  home-manager, любой в режиме `mode off`), запускается сразу там, откуда
  ссылка, — в спросившей зоне и в контейнере спросившей программы, как
  запустил бы его `xdg-open` там; сеть не пересекается. Программе без
  известного контейнера (одноразовой песочницы) — в собственном профиле
  зоны, где его и раньше запускал `xdg-open` в зоне.

**«Всегда» — по контейнеру.** В окне запуска — своя галочка «Всегда
открывать ссылки <схема>: из контейнера <к> в <программа>»: правило
`link = <схема> <id>` контейнера (Nix `containers.<к>.links.<схема>`,
локально `cellward container links <к> set|rm`, в `status` —
`containers[].links`). Оно пропускает только выбор программы — окно сети и
контейнера остаётся. Системное умолчание хоста CellWard не меняет никогда;
галочка «Назначить по умолчанию» в окне KDE — его, дистрибутива.

**Чей контейнер.** Фильтр шины зоны знает контейнер каждого соединения
(`origin`) и говорит его брокеру; брокер верит этому слову только от самого
фильтра — процесса, чей родитель — процесс зоны (`zone.pid`): программа зоны
таким быть не может, она входит с хоста через `nsenter`, а сирота уходит
жнецу хоста. Любому другому брокер определяет контейнер сам, по запуску,
из которого вышел спросивший (фильтр песочницы — часть её запуска).
Собственные программы зоны (`main`) и неизвестные — без правила, выбор
каждый раз. Песочница на хосте брокеру не зона: её ссылки открывает её
фильтр, как раньше (`xdg-open`).

**Вопросы считаются.** Выбор программы — вопрос, как и окно запуска: один за
раз на весь хост (оба окна одной ссылки — под одним), не больше стольких-то
за окно времени от одной зоны, и после «нет» (закрытое окно выбора) зона
какое-то время не спрашивает. Ссылка, для которой спрашивать нечего
(правило и неперехваченный ярлык), вопросом не считается.

Не держит пока: окно выбора программы не называет зону (у AppChooser нет
для этого места — зону называет следующее окно); контейнер в окне запуска
не предвыбирается по тому, откуда ссылка; окно выбора программы, оставленное
открытым, держит очередь вопросов, пока его не закроют (срока нет —
владелец против жёстких сроков).

### 11.14 Сеть допускает, контейнер просит (владелец, 2026-09-28)

Независимое ревью 2026-09-28 нашло, что разделение «сеть — изоляция
программ» сломано в обе стороны. Настройки программ (X11 и умолчания для
остального) решала сеть. Обходы сети (Nix-демон, отказ от
герметичности, запись файлов хоста) контейнер мог получить сам, и тогда
они действовали в любой сети: в offline, в строгой VPN-зоне, в запертой.
Сеть не могла им отказать. Владелец принял модель:

- **У сети** — транспорт, DNS, маршруты, замок и то, какие обходы она
  **допускает**: подмножество {сессия хоста (без герметичности),
  Nix-демон, запись файлов хоста}. По умолчанию — ничего. `offline` не
  допускает ничего, что бы ни было задано: дорога мимо сети — уже сеть.
  Запертая зона (`cellward lock`) не допускает сессию хоста: замок держит
  брокер, а программе с `systemd --user` брокер не нужен.
- **У контейнера** — разрешения программ (X11, камеры, микрофон, экран,
  менеджер звука, фокус, цвет) и **просьбы** об обходах.
- **Действует** обход, только если контейнер его просит и сеть
  допускает. Нечитаемое значение — «нет». Своё «нет» контейнера
  закрывает обход в любой сети.
- **Основной дом** получит свою запись политики (`containers/main`),
  **разовые** — шаблон разрешений программ (`defaults.permissions`) и
  никогда — обходов.

Nix-демон — это способность программы с сетевым побочным эффектом. Он
нужен только некоторым программам (терминалу, Claude Code, direnv), но
качает он в сети хоста, а у пользователя из `trusted-users` он ещё и
равен root хоста. Поэтому нужны оба ключа. Так же устроены сессия хоста
и запись файлов хоста.

**Переход без расширения прав.**

0. Исправления (**сделано**, 2026-09-28): смена сети на ходу не уносит
   замороженные настройки шире, чем дала бы новая сеть; местное «строже»
   берёт верх над Nix сети; разовые поднимаются с безопасными значениями;
   `x11` — да, нет или как у сети; замок пускает только герметичных;
   `doctor` предупреждает о Nix-демоне у доверенного пользователя.
1. **Совместимость и допуск (сделано**, 2026-09-28,
   `hermetic::tolerance`, `hermetic::explain`). Прежние списки и маркеры
   зон (`hermetic.exceptions`, `nixDaemon`, `hostFilesWritable`,
   `cellward hermetic|nix-daemon|host-files <зона>`) означают сразу два
   слова. Сеть это допускает. А основной дом и контейнер без своего слова
   это просят. Для каждого нынешнего запуска результат прежний.
   Своё «да» контейнера теперь действует только в сети, которая его
   допускает: раньше оно открывало обход где угодно. `offline` не
   допускает обходов вовсе, запертая зона — сессию хоста. Менеджер
   звука остаётся разрешением программы: контейнера, а без своего слова —
   сети. `cellward explain <контейнер|программа|main> [<сеть>] [--json]`
   показывает, что получают программы и чьё слово это решило. `status
   --json` показывает, что допускает сеть: `networks[].tolerates`.
   `cellward container set` говорит, если сеть контейнера просьбу не
   допускает. Модуль больше не называет эти списки устаревшими: это
   допуск сети. Он предупреждает, если в них назван offline.
2. У основного дома своя запись разрешений: `cellward container set main
   <настройка> …` локально, `programs.cellward.main.permissions.*` в Nix — по
   образцу `containers.<имя>.permissions` (владелец, 2026-09-28: названия на
   моё усмотрение). Затем `cellward migrate permissions --dry-run|--apply`:
   записать явные просьбы тем контейнерам и основному дому, которые сейчас
   получают обход по списку сети; модуль делает то же для объявленных. Что
   расширило бы права в другой сети, только предлагается.
3. Списки означают только допуск (`networks.<з>.allow`), затем уходят;
   поля программ у сети уходят из `status` в схеме 2.
4. Экземпляры для `unconfined`: изоляция программ и там.

Проверка шага 1 — перебор всех сочетаний в тесте
`hermetic::tests::a_way_around_the_network_needs_both_words`. Он
перебирает сеть (обычная, запертая, offline), её слово и слово контейнера
(нет, да или нет, местно или из Nix) и того, кто запускает (основной
дом, контейнер, никто). Проверяется: ничего не шире шага 0, обход открыт
только при просьбе и допуске, «нет» контейнера держится, без своего
слова результат прежний.

### 11.15 Изоляция — только у контейнера (владелец, 2026-09-29)

Второе независимое ревью (2026-09-28) и разговор с владельцем
2026-09-28–29 уточнили цель. Она заменяет шаги 2–4 из §11.14.

**Цель.**
- Каждая программа запускается в своём контейнере, и контейнеры изолированы
  друг от друга и от хоста во всём.
- Изоляция — дело контейнера, по осям: файлы, устройства, камера, микрофон,
  показ экрана, окна и ввод, сеанс компьютера, сертификаты, Nix-демон.
- **Сеть** — только куда идут пакеты: без сети, напрямую (сеть хоста) или
  VPN. Слово «зона» больше не употребляется: это просто выбранная сеть.
- VPN — не изоляция. «Без изоляции» — отдельный явный выбор, и он совместим
  с любой сетью.
- Сеть может запретить только то, что обходит её туннель:
  - полный сеанс компьютера;
  - Nix-демон;
  - запись в то, что исполняет хост;
  - сетевые устройства (телефон-модем, USB-сетевая карта).
- Камеру, микрофон, клавиатуры и геймпады сеть не запрещает никогда.
- Разрешения **спрашиваются** там, где есть посредник:
  - микрофон, камера, показ экрана;
  - устройства — при открытии, в том числе подключённые позже;
  - сеть — первое соединение программы.

  Микрофон, пока не разрешён, тихий, камера — чёрная, устройство видно, но
  не открывается. После «нет» программу не спрашивают снова, пока человек
  не изменит это в меню окна (☰). Таймера нет.
- **Файлы** выдаются при запуске и через ☰ папками, в режиме только чтения,
  слоя или полного доступа. Отдельные файлы — через портал выбора файла.
  Какой у контейнера дом, решается только до старта.
- **X** — свой у каждого контейнера и поднимается сам, когда программа к нему
  обращается. X хоста не даётся никогда.
- **Ядро сеанса** работает на хосте. Это короткий список: niri, порталы,
  PipeWire с WirePlumber и pipewire-pulse, агент polkit, `systemd --user`,
  шина, cellward и stillconf. Службы программ из `systemd --user`
  переезжают в контейнеры.

  noctalia — в свой контейнер «оболочка» с особым набором разрешений.
  `doctor` показывает всё, что работает вне контейнеров и не входит в ядро.

**Порядок работ.**
1. Дыры (**сделано**, 2026-09-29, LEAK-MODEL §32): то, что исполняет хост,
   и список человека (`cellward protect`) закрыты для контейнеров
   настоящего дома; кэш Nix у них свой; «без ограничений» названо как есть.
2. Разрешения только у контейнера:
   - а) **У «основного» своя запись без сети** (`containers/main`):
     `cellward container set|show|devices|grant main …`,
     `programs.cellward.main.*`. В каждой сети у него своё пространство
     (`main:<сеть>`), а разрешения — одни. «Всегда» для программы в нём
     закрепляет программу, а не создаёт контейнер `main-<сеть>`.
   - б) **Разрешения программ без сети** (микрофон, трансляция экрана,
     камеры и менеджер звука — **сделано**, 2026-09-29,
     `rust/src/permissions.rs`; X — вместе с «X по требованию»). Действует
     своё слово контейнера,
     иначе общий шаблон (`programs.cellward.defaults.permissions`,
     `cellward defaults set`), иначе встроенное безопасное значение.
     Настройки сети `camera|microphone|screencast|audio-manager|x11 <сеть>`
     и их опции Nix уходят. Однократный перенос не расширяет права: контейнер
     привязанной сети получает её прежнее значение как своё, а «основной» и
     непривязанные — самое узкое из значений сетей. Всё сузившееся
     записывается в журнал.
   - в) **Допуск сети** (**сделано**, 2026-09-29). Списки
     `hermetic.exceptions`, `nixDaemon`, `hostFilesWritable` значат только
     допуск. Просьбы, которые шим шага 1 приписывал «основному» и
     контейнерам без слова, теперь явные. Они записаны не в каждую запись,
     а в одно видимое место — шаблон просьб (`cellward defaults set
     hermetic|nix-daemon|host-files …`, `programs.cellward.defaults.
     permissions.*`). Один раз шаблон получил то, что просили списки. Так
     поведение прежнее, но видно, кто что просит, и шаблон можно сузить,
     оставив просьбу только нужным контейнерам. Пространство самой зоны
     поднимается по допуску сети.
   - г) **Слова** (**сделано**, 2026-09-29). «Основной дом» становится
     «Настоящим домом» и при выборе говорит, что откроется (ключи ssh,
     пароли браузера, токены). Слово «зона» уходит из интерфейса.
   - д) **«Без ограничений» — только сеть.** Это пространство контейнера с
     сетью хоста, а настройки контейнера действуют и там. «Без изоляции» —
     отдельный явный выбор.
     - **Сеть хоста** (**сделано**, 2026-09-29): встроенная сеть `host` —
       зона, где pasta идёт по маршрутам хоста и спрашивает его резолвер.
       Она везёт экземпляры контейнеров, как любая сеть, и допускает все
       обходы: обходить в ней нечего, решает слово контейнера. Её зона
       создаётся, когда понадобилась; зона человека с таким именем не
       перезаписывается, а запуск в неё отказывается.
     - **Без изоляции** (**сделано**, 2026-09-29): встроенная запись `open`
       (`cellward run <сеть> --no-isolation`, в окне запуска — строка «Без
       изоляции»). Это контейнер настоящего дома, где открыто всё:
       - сессия хоста, Nix-демон, запись того, что исполняет хост;
       - все устройства, в том числе подключённые позже (devtmpfs хоста
         поверх `/dev` запуска; свои терминалы остаются);
       - камеры, микрофон, показ экрана, звук, свой X;
       - весь дом выдан, так что снят и список `cellward protect`.

       Работает в любой сети, в том числе с VPN. Обходы туннеля по-прежнему
       решает сеть (допуск): в сети, которая их не допускает, они закрыты, и
       это сказано. Запись пишется заново перед каждым запуском и не
       настраивается; кому нужно не всё — контейнер настоящего дома.
     - `unconfined` остаётся «без изоляции и без VPN» — прежний запуск прямо
       на хосте, без пространства.
3. Окно запуска — галочки по осям (по умолчанию всё запрещено), каталог
   заготовок по программам (безопасное из заготовки применяется само,
   опасное спрашивается; `programs.cellward.programs.<id>`; stillconf их
   показывает), меню ☰ — выпадающее, с теми же осями на ходу.
   - а) **Каталог заготовок** (**сделано**, 2026-09-29, `rust/src/presets.rs`,
     `cellward presets [<id>] [--json]`). Заготовка — что нужно программе,
     по id ярлыка. Безопасное (вопросы о микрофоне и экране, свой X,
     геймпады, ключи безопасности) её свой контейнер получает сам, когда
     создаётся, и только там, где у него нет своего слова. Остальное
     (камеры, папки, устройства со своей сетью, сеанс хоста, Nix-демон,
     запись того, что исполняет хост, сырой PipeWire, дом с настоящим)
     только предлагается. Заготовка из Nix
     (`programs.cellward.programs.<id>`) заменяет встроенную целиком.
   - б) **Предложенное — галочками** (**сделано**, 2026-09-29). Окно
     запуска показывает предложенное заготовкой галочками, снятыми по
     умолчанию; отмеченное становится словом выбранного контейнера —
     своего контейнера программы (он создаётся с безопасной частью
     заготовки) или именованного. Засчитывается только то, что заготовка
     предлагает. Окно, поднятое программой из сети, не предлагает ничего.
   - в) Меню ☰ — выпадающее.
4. «Спросить» с подменой: тихий микрофон с выбором источника, чёрная
   камера, устройства при открытии и на лету, сеть при первом соединении.
5. Файлы папками: только чтение, слой, полный доступ; сокеты в выданных
   папках закрыты.
6. Настройки на ходу — рамка, в том числе нулевой ширины, через inotify у
   надзирателя запуска. Обновление не убивает программ. Окна cellward
   плавают без правил композитора: фиксированный размер у окна запуска,
   xdg_popup у меню.
