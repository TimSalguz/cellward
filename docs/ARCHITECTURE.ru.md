# Целевая архитектура: всё по умолчанию в контейнерах

English: [ARCHITECTURE.md](ARCHITECTURE.md) · Связанное: [LEAK-MODEL.md](LEAK-MODEL.md),
[CONTAINERS.ru.md](CONTAINERS.ru.md), [SYSTEM.md](SYSTEM.md) (системный уровень, M10)

**Статус: целевая картина, 2026-09-23.** Документ описывает, куда идёт проект.
У каждой части ниже сказано, есть ли она уже; всё, что не помечено как сделанное,
пока план.

## 1. Цель и единственная уступка

Каждая программа и каждая служба получают ровно то, что им нужно: свои файлы,
одну сеть, выданные устройства. Всё остальное закрыто по умолчанию, а исключения
явные и видные. Утечки невозможны по построению, а не запрещены правилом
([LEAK-MODEL.md](LEAK-MODEL.md)).

Самая сильная изоляция — своя виртуальная машина на каждую программу (Qubes OS,
Spectrum OS). Здесь её нет сознательно: одна видеокарта, игры и задержки звука
несовместимы с виртуалкой на всё. Поэтому граница — **namespaces ядра**, и ядро у
всех общее. Это единственная уступка. Устройство при этом взято у Qubes: хост —
пустая «диспетчерская», работа идёт в отсеках, сеть приходит в отсеки через
отдельные шлюзы.

## 2. Пять понятий

```
┌──────────────────────────── ХОСТ («диспетчерская») ──────────────────────────────┐
│  ядро, systemd, композитор, nix-daemon, движок vpn-zones, окно настройки         │
│  своей сети нет: наружу выходят только аплинки зон и явно разрешённые службы     │
│                                                                                  │
│  ВАХТЁР ← лаунчер, бинды композитора, ссылки, D-Bus, автозапуск, терминал,       │
│     │     набранная команда, запуск из скрипта                                   │
│     ▼     «кто это и куда его?» → помнит / объявлено в Nix / спрашивает          │
│  ┌─ контейнер программы ─┐ ┌─ контейнер-терминал ─┐ ┌─ служба / NixOS-система ─┐  │
│  │ bwrap: свой дом,      │ │ всё набранное в нём  │ │ песочница systemd или    │  │
│  │ папки, фильтр шины    │ │ наследует его        │ │ nspawn                   │  │
│  └──────────┬────────────┘ └──────────┬───────────┘ └────────────┬─────────────┘  │
│             ▼                         ▼                          ▼                │
│  ═══ ЗОНЫ: в каждой ровно два пути — lo и единственный выход зоны ═══            │
│   offline │ unconfined │ WireGuard/AmneziaWG │ OpenConnect │ интерфейс хоста      │
│   зоны пользователя (держит сеанс)        системные зоны (держит systemd)         │
└──────────────────────────────────────────────────────────────────────────────────┘
```

1. **Зона — какая сеть.** Namespace, в котором есть `lo` и один выход. Туннель
   создаётся в аплинке и переезжает внутрь, поэтому его сокет и адрес сервера
   программам не видны. *Есть* для пользовательского уровня.
2. **Контейнер — что программа видит.** Дом, выданные папки, устройства,
   доверенные сертификаты, фильтрованная шина, свой Wayland-сокет. Три
   исполнения одной идеи:
   - программа рабочего стола — bwrap (*есть*, [CONTAINERS.ru.md](CONTAINERS.ru.md));
   - одна служба — её собственный юнит с песочницей systemd (*нет*, M10);
   - целая система со своими службами и пользователями — nspawn,
     `containers.<имя>` NixOS (*нет*, M10).
   Любой контейнер подключается к любой зоне своего уровня, к одной в каждый момент.
3. **Вахтёр — кто решает.** Все способы запуска сходятся в одну точку, которая
   знает, какой программе какой контейнер и какая зона положены. Про незнакомую
   спрашивает один раз и запоминает. **Внутри контейнера всё наследуется**:
   `ls | grep` в терминале ничего не спрашивает, потому что терминал уже в
   контейнере. *Частично есть* (§5).
4. **Запросы на лету.** Как на Android: файл, камера, микрофон — системным
   диалогом с именем программы. Файлы *уже* так работают (порталы). Сеть так не
   выдаётся по построению: namespace выбирается при запуске, смена сети — это
   перезапуск.
5. **Страховка.** Хост без сети по умолчанию: наружу выходят только аплинки зон
   и службы из списка. Даже то, что проскочило мимо вахтёра, сети не имеет. Плюс
   журнал: кто, куда, когда (*журнал есть*, политики на выход пока нет).

## 3. Два уровня — одна зона

| | Пользовательский уровень | Системный уровень |
|---|---|---|
| Модуль | home-manager (`homeModules.default`) | NixOS (`nixosModules.default`) |
| Права | без root | root |
| Держатель зоны | `vpn-zone@<имя>` пользователя, живёт с сеансом | `vpn-zone-system-<имя>` системы, живёт с загрузки |
| Аплинк | отдельный namespace за pasta | сеть хоста |
| Namespace приложений | принадлежит user namespace зоны | `/run/netns/vz-<имя>` |
| Конфиг | `~/.local/state/vpn-zones/<имя>/config.conf` | `/var/lib/vpn-zones/system/<имя>/config.conf` или путь к секрету |
| Кто подключается | программы пользователя | службы, NixOS-контейнеры; программы — через посредника (позже) |

**Общее — всё остальное:** формат конфига, разбор (`config.rs`), разрешение
endpoint в сети хоста до настройки, туннель создаётся снаружи и переезжает внутрь,
внутри `lo` + `awg0` и ничего больше, тот же набор правил второго эшелона, тот же
resolv.conf из `DNS =`, тот же смоук-ассерт «ровно два линка», один документ
`vpn-zone status --json`.

**Что объединить нельзя, и это видно человеку:**
- Службу нельзя положить в зону пользователя: такая зона умирает с сеансом.
- Программа пользователя без root не войдёт в системную зону: `setns` в namespace,
  которым владеет root, требует прав. Нужен крошечный посредник — войти в
  namespace, сбросить права до пользователя и выполнить обычный запуск vpn-zones с
  песочницей. Это новая поверхность атаки, поэтому посредник минимален,
  включается только системным модулем и пускает только тех, кого разрешили.

Пользовательский уровень от системного не зависит. Кто не хочет root-части, не
включает NixOS-модуль, и для него всё остаётся rootless, как сейчас.

## 4. Хост и консоль (TTY)

Хост — место для администрирования: `nixos-rebuild`, окно настройки, откат. Когда
страховка из §2 включена, **у оболочки хоста сети нет, и в TTY тоже.** Это
задумано, а не побочный эффект:

- администрирование продолжает работать: скачивает не оболочка, а nix-daemon, он
  в списке разрешённых. Пересборка, откат и `nix-collect-garbage` из TTY работают;
- сеть в TTY при необходимости берётся так же, как везде: `vpn-zone run <зона> --
  bash` (менеджер пользователя systemd запускается и для входа в TTY, так что
  пользовательские зоны там работают) или системная зона через посредника;
- аварийный ключ: «открыть хост на 15 минут» — юнит с автоматическим возвратом,
  как подтверждение с откатом у пересборки;
- `strict` отнимает сеть и у служб самого хоста: root остаётся локальная сеть,
  а nix-daemon и часы ходят через свою зону (простая — напрямую, или VPN);
- выключатель: `vpn-zones-off` выключает всё на месте — без пересборки, которой
  могла бы понадобиться та самая сеть, что держит политика, — до `vpn-zones-on`;
- ловушкой это не станет: политика — это юнит, откат поколения из меню загрузки
  снимает её вместе со всем остальным.

## 5. Где появляется вопрос

| Как запускается | Как ловится | Состояние |
|---|---|---|
| Лаунчер, ссылки (`xdg-open`), D-Bus-активация, автозапуск | перехват записей, тени сервисов | **есть** (M8) |
| Бинды композитора | `vpn-zone launch <id>` вместо программы | **механизм есть**, бинд правит человек |
| Терминал | сам терминал запускается в контейнере с выбором сети; набранное наследует | **механизмы есть** (дом `overlay`), не собрано вместе |
| Программа, набранная в терминале | PATH-шимы; хук оболочки перед строкой | **шимы есть** (`pathShims.enable`), хука нет |
| Запуск из скрипта, файлового менеджера, чужой программы | fanotify `FAN_OPEN_EXEC_PERM` от root: запуск ждёт ответа демона | **нет**, последним |

Ядро умеет запуск **разрешить или запретить, но не перенаправить**. Поэтому ответ
«в контейнер» на последней строке выглядит так: исходный вызов получает ошибку, а
программа стартует заново в контейнере. Для интерактивного запуска это нормально,
для скрипта — нет.

## 6. Контроль запусков — не изоляция

- bash умеет сеть сам: `exec 3<>/dev/tcp/хост/80` — без единого нового бинарника.
  То же `python -c` и любой интерпретатор;
- запуск через загрузчик (`ld-linux.so ./программа`) и из `memfd` не открывает
  файл как исполняемый и мимо проверки проходит;
- упавший fanotify-демон — и ядро пропускает всё: этот слой по природе не
  «закрыт при сбое».

Поэтому вахтёр — **слой удобства**: он направляет и подсказывает. Границу держат
namespaces (сеть и файлы контейнера) и политика хоста на выход. Исключения вахтёра
задаются **пакетом в сторе, а не именем**: `~/bin/bash` может положить кто угодно
(тот же урок, что allowlist Wayland по имени бинаря, LEAK-MODEL §8).

## 7. Что есть и чего нет

| Часть | Состояние |
|---|---|
| Зоны пользователя, шлюзовая схема, второй эшелон, герметичность | есть |
| Контейнеры программ, перехват запусков, сертификаты по контейнерам | есть, хвосты M8 |
| Машиночитаемое состояние и декларативные опции | есть (`status --json`, home-manager) |
| Системные зоны | есть (M10, этап 1) |
| Службы и NixOS-контейнеры в системных зонах | есть (M10, этапы 2–3) |
| Посредник «программа пользователя в системной зоне» | консольные — есть (`vpn-zone-sys`), графические — M10, этап 4 |
| Хост без сети по умолчанию | есть (M10, этап 5: `egress`, сначала `audit`); резолвер хоста — следом |
| Пульт TTY: сеть сразу после входа | есть (`console`, SYSTEM.md §7a) |
| Терминал в контейнере, хук оболочки | M10, этап 6 |
| Вахтёр для запусков из скриптов (fanotify) | M10, этап 7, после замеров |
| Запросы камеры и микрофона на лету | M8, хвост |

## 8. Кто за что отвечает

vpn-zones — движок обоих уровней: код, модули, проверки на утечки, одна модель
утечек. Окно настройки (nix_cm) — только окно: читает `vpn-zone status --json` и
пишет опции модулей, как уже делает с контейнерами программ. Проверки герметичности
живут в одном месте — здесь.

Правило ключей одно для обоих уровней: **ключи зон в Nix не объявляются.**
Системная зона — локальное состояние (`/var/lib/vpn-zones/system/`), как
пользовательская — своё. Путь к секрету (sops-nix, agenix) — необязательный путь
для тех, кому нужна воспроизводимость: тогда в репозитории лежит только
зашифрованный файл.
