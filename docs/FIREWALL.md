# Сетевой монитор и фаервол: проект

Дата: 2026-09-28. Проект до кода по просьбе владельца: «фаервол, насколько
хорошим его можно сделать», с оглядкой на GlassWire (наглядность) и RethinkDNS
(правила), и с его идеей видеть трафик каждой программы внутри контейнера и
разрешать двум программам только определённые взаимодействия. Кода пока нет.
Делать после шагов 0–1 новой модели прав (docs/PERMISSIONS.md §11, «сеть терпит
обходы, контейнер их просит»): правила фаервола — тоже права контейнера и должны
лечь в ту же модель.

## 0. Что есть сейчас

- **Фаервол от утечек** (ROADMAP M3): nftables в каждой зоне. Программы выходят
  только в туннель, сам туннель — только к серверу VPN. Это защита обещания
  зоны, а не инструмент человека: ни показать, ни настроить его нельзя, и так
  задумано.
- **Хост без своей сети** (системный уровень, `services.cellward.system.egress`):
  программа вне зон не выходит никуда. Строгий режим закрывает и системных
  пользователей.
- **Контейнер привязан к своей сети.** Есть `offline`. Сеть контейнера меняется
  на ходу.
- **Счётчики трафика зоны** в `status --json` (`rx_bytes`, `tx_bytes`).
- **Чего нет:** учёта по контейнеру и программе, журнала соединений, правил
  «этой программе можно только туда», вопроса при первом выходе в сеть, ленты
  тревог, окна, где всё это видно.

## 1. Откуда идеи

| Источник | Что берём | Чего не берём |
|---|---|---|
| **GlassWire** (Windows) | наглядность: шкала трафика во времени с отметками программ на всплесках; расход по программам, хостам и видам трафика; лента тревог («впервые вышла в сеть», «новый хост»); переключатель сети у каждой программы | оформление; правила у него простые, их берём у Rethink |
| **RethinkDNS** (Android, Apache 2.0, сетевое ядро firestack на Go) | правила по программе (запрет, доверие или блок IP и доменов); общие правила: «когда устройство заблокировано», «когда программа не используется», «UDP только DNS и NTP», «блокировать, если DNS обойдён»; списки блокировки DNS по категориям (безопасность, приватность, родительский); журнал соединений по программам с пометкой подозрительных; разные туннели разным программам | код: у них Kotlin/Go для VpnService Android, у нас Rust и другая точка перехвата |
| **Little Snitch / OpenSnitch** | режим «спросить при первом соединении»: программа, адрес, порт; ответ «однажды / всегда / никогда» | вопрос на каждый пакет: только на новое |

Где cellward может быть лучше их всех — за счёт устройства (§2):
- **Правило нельзя обойти.** Правила применяются вне пространства имён
  программы, на нашей пересылке и в нашем DNS. На Android правило держит
  VpnService, на Windows — фильтр всей машины.
- **У каждого контейнера своя сеть и свои правила.** Контейнер «работа» через
  корпоративный VPN со своими правилами, «банк» в своём, их трафик и журналы не
  смешиваются.
- **«Только IP из нашего DNS» проверяется жёстко.** Каждый запрос имён
  контейнера идёт через наш пересыльщик, так что известно, какие адреса он
  получил законно. Соединение с адресом, которого не было ни в одном ответе, —
  прямой IP или зашитый DoH, и его можно запретить. Журнал доменов тогда
  полный.

## 2. Где стоит движок

Три места, через которые трафик контейнера проходит обязательно и которые
программе не подвластны:

1. **Пересылка экземпляр ↔ зона** (`crate::relay`, passt в зоне). Каждый кадр
   контейнера проходит через неё. Здесь учёт по контейнеру и удержание
   соединения на время вопроса «спросить» (§4.3).
2. **Пересыльщик DNS экземпляра** (постоянный адрес D4/D6 в `resolv.conf`
   экземпляра, `crate::bridge`). Здесь журнал доменов, списки блокировки,
   соответствие «адрес → имя» для монитора и набор законных адресов для
   «только IP из нашего DNS».
3. **nftables в сетевом пространстве экземпляра** (хранитель держит там
   CAP_NET_ADMIN). Здесь счётчики и правила по программе: по cgroup запуска
   (§3). Модуль `nft_socket` уже проверяется пробой живой смены сети; без него
   правила по программе недоступны и об этом говорится прямо (при сбое всё
   закрыто: правило «запретить» без модуля — отказ запуска, а не молча
   «разрешить»).

Движок — часть cellward: это код безопасности, при сбое всё закрыто. Окно-монитор
(§6) — тоже cellward, чтобы работать и без stillconf. stillconf правит правила и
открывает монитор.

## 3. Учёт: зона → контейнер → программа → процесс

- **Контейнер:** счётчики пересылки экземпляра (байты и пакеты в обе стороны),
  без модулей ядра.
- **Программа внутри контейнера — без вложенных контейнеров.** У каждого запуска
  своя cgroup внутри cgroup экземпляра: `…/e<эпоха>/l<запуск>`, куда процесс
  кладётся при рождении (`clone3(CLONE_INTO_CGROUP)`, как уже кладётся в эпоху).
  Счётчики nftables по `socket cgroupv2 level … "…/l<запуск>"` в пространстве
  экземпляра. Так у каждого запуска свой трафик, а общий дом, общий `/tmp`,
  одна копия программы и перетаскивание между программами остаются.
- **Соединения:** sock_diag в пространстве экземпляра (`crate::sockdiag` уже
  умеет перечислять) → inode сокета → процесс (через `/proc/<pid>/fd` в
  пространстве процессов экземпляра) → запуск (по cgroup процесса).
- **DNS по программе:** пересыльщик видит порт источника запроса, порт — это
  сокет, сокет — процесс. Так видно, какая программа какое имя спросила.
- **Процесс:** для «кто именно» в списке соединений (например, вкладка браузера
  против расширения — нет; процесс браузера против его помощника — да).

## 4. Правила

### 4.1 Уровни и направление

- **Сеть (зона)** — общие правила для всех её контейнеров: только сужают.
- **Контейнер** — для всех его программ.
- **Программа** (id ярлыка) внутри контейнера.
- Правило только **сужает** то, что позволил уровень выше. Правило фаервола
  никогда не открывает обход туннеля: обходы — отдельная модель прав («сеть
  терпит, контейнер просит»).
- Порядок как у остальных прав: Nix важнее местного; местное, которое строже,
  выигрывает у менее строгого Nix выше по уровню (шаг 0 модели прав).

### 4.2 Виды правил

| Правило | Где применяется | Откуда идея |
|---|---|---|
| сеть: да / нет | nft по cgroup запуска; контейнер — пересылка | GlassWire, Rethink |
| домены и IP: разрешить / запретить, списки | DNS (домены), nft (адреса) | Rethink |
| **только IP из нашего DNS** | nft: набор законных адресов на контейнер, пополняется пересыльщиком из ответов; срок записи — TTL ответа (срок из данных, не зашитый) | Rethink «блокировать, если DNS обойдён» |
| UDP только DNS и NTP | nft | Rethink |
| без сети, пока экран заблокирован | состояние блокировки сеанса (logind `LockedHint`) → хранитель переключает правило | Rethink «когда устройство заблокировано» |
| без сети, пока ни одно окно программы не на экране | посредник Wayland знает окна запуска (рамка) и их состояние; позже | Rethink «когда не используется» |
| списки блокировки DNS по категориям | пересыльщик экземпляра | Rethink |
| спросить при первом соединении | пересылка (§4.3) | Little Snitch |

### 4.3 «Спросить»

- **Что спрашиваем.** Первое соединение программы вообще, или первое к новому
  домену (выбирается у контейнера). Не каждый пакет.
- **Где держим.** На пересылке: первый пакет нового потока (SYN, первый
  UDP-пакет) задерживается, остальные этого потока ждут. Спрашивает окно запуска
  (тот же охраняемый вопрос, что у сети и контейнера): «Firefox в «работа» хочет
  к example.com:443 — однажды / всегда / никогда».
- **Без таймеров, решающих исход.** Держится столько, сколько открыт вопрос;
  закрыт без ответа — «нет». TCP сам повторит SYN, если человек ответил «да»
  позже.
- **Когда вопрос нельзя показать** (нет сеанса, окно не открывается) — «нет»
  при сбое, и уведомление, когда оно возможно.

### 4.4 Списки блокировки

- Списки — чужие данные со своими лицензиями (например, OISD). Кладём их
  ссылками с хешами, как любые данные в Nix, или берём из nixpkgs, если там есть.
- Скачивание — только через зону и только с закреплённым хешем. Хост сам никуда
  не ходит.
- Категории как у Rethink: безопасность, приватность, трекеры, родительский.
  Выбираются у контейнера.

## 5. Взаимодействия программ

Контейнер — общий дом: общие файлы и `/tmp`, одна копия программы. Поэтому:

- **Программам нельзя свободно общаться → разные контейнеры.** Вложенные
  контейнеры не нужны: они отняли бы у контейнера смысл, а изоляции не
  прибавили бы по сравнению с двумя соседними.
- **Мосты между контейнерами** — только названное, в одну сторону, видно в окне:
  - **общий каталог** — есть (`cellward container grant`);
  - **имя на шине D-Bus** — контейнеру A разрешено говорить с конкретным
    именем, которое держит программа контейнера B (правило фильтров шины обоих
    экземпляров);
  - **сокет** — конкретный unix-сокет экземпляра B, привязанный в экземпляр A.
    Пример: расширение KeePassXC в браузере контейнера «веб» говорит с
    KeePassXC в контейнере «пароли» — и больше ни с чем, а браузер не видит
    ни дома, ни файлов «паролей»;
  - **нативные помощники браузера** (native messaging) — как сокет, через
    посредника.
- **Мягкие стенки внутри контейнера** (позже): Landlock у каждого запуска (он уже
  есть для сигналов и абстрактных сокетов) расширяется до путей дома —
  программа A не читает каталог программы B; фильтр шины — правила по
  программе. Полной изоляции не даёт: для неё — отдельный контейнер.

## 6. Окно-монитор

Раскладка — по идеям GlassWire, свой вид (cellward, iced, как окно запуска):

```
┌ Сеть cellward ──────────────────────────────────────────────────────┐
│ [График] [Соединения] [Расход] [Правила] [Тревоги] [Мосты]  ⏸ 1ч ▾ │
├──────────────────────────────────────────────────────────────────────┤
│  ▁▂▃▅▇█▇▅▃▂▁▁▂▃▂▁      ← шкала: сверху приём, снизу отдача,       │
│  ▔▔▔▀▀▀▔▔▔▔▔▔▔▔▔▔        цвет — контейнер (цвет рамки)            │
│      ↑ Firefox (работа) 12 МБ    ↑ Telegram (личное) впервые       │
├──────────────────────────────────────────────────────────────────────┤
│ Сейчас в сети:                                                        │
│  ● работа   Firefox     example.com  443  ↓2,1 МБ ↑40 КБ  3 мин       │
│  ● личное   AyuGram     api.telegram…  443  ↓120 КБ         1 ч       │
└──────────────────────────────────────────────────────────────────────┘
```

- **График** — шкала по контейнерам и программам; отметки на всплесках и на
  «впервые».
- **Соединения** — живой список: контейнер, программа, процесс, имя (из нашего
  DNS), адрес, порт, объём, давность, зона. Действие по строке: «запретить
  этот домен этой программе».
- **Расход** — день / неделя / месяц по контейнеру, программе, зоне, хосту.
- **Правила** — по контейнерам и программам, с переключателями и источником
  (Nix / местное).
- **Тревоги** — лента: программа впервые вышла в сеть; контейнер обратился к
  новому хосту; соединение в обход нашего DNS (при правиле «только IP из DNS»
  — отказ); всплеск; правило сработало; туннель зоны умер.
- **Мосты** — что между контейнерами открыто.
- Метка трея и `cellward focused --bar` могут показывать «в сети сейчас».

## 7. Журнал и приватность

- **Только локально.** `~/.local/state/vpn-zones/netlog/`, закрыт от зон, как
  остальное состояние.
- **Два слоя.** Итоги (байты по контейнеру, программе, хосту, дню) хранятся
  дольше. Сырой журнал (каждое соединение, каждый запрос имени) — коротко.
- **Сроки — решение владельца** (открытый вопрос §10). Есть «не вести журнал
  доменов» у контейнера.
- **Вывод:** `cellward traffic --json [--watch]` для окна, stillconf и панелей;
  схема — в `status`-стиле, `{value, source}` для правил.

## 8. Наружу

- `cellward traffic [--json] [--watch] [--container <к>] [--program <id>]`.
- `status --json`: у контейнера — правила и итоги; у экземпляра — живые
  счётчики.
- Nix: `programs.cellward.containers.<к>.firewall = { …; }`,
  `programs.cellward.firewall.defaults`, `networks.<з>.firewall` (только
  сужение). stillconf правит и показывает.

## 9. Этапы

1. Учёт по контейнеру (счётчики пересылки) и `cellward traffic --json`.
   **Счётчики — сделано** (2026-09-28, `rust/src/traffic.rs`): пересылка
   считает каждый кадр в файл `traffic` экземпляра через общее отображение,
   без системных вызовов; `cellward traffic [--json] [--watch]`,
   `status --json` — `instances[].traffic`. Дальше — история по дням и сетям
   (итоги §7) и сроки хранения.
2. cgroup у каждого запуска, учёт по программе, соединения, DNS по программе.
3. Окно-монитор: график, соединения, расход.
4. Правила: сеть да/нет, домены и IP, «только IP из нашего DNS», UDP только
   DNS/NTP, «без сети при заблокированном экране».
5. «Спросить» на пересылке.
6. Списки блокировки, тревоги.
7. Мосты между контейнерами.
8. Мягкие стенки внутри контейнера (Landlock по путям, шина по программе).

## 10. Открытые вопросы владельцу

1. Сроки хранения: итоги и сырой журнал.
2. Режим по умолчанию для новой программы: «разрешить и показать» или
   «спросить».
3. Списки блокировки: какие категории включать по умолчанию и откуда брать.
4. Монитор: всегда работает (учёт копится) или только когда окно открыто.

## 11. Риски

- **Нагрузка на пересылку:** каждый кадр контейнера — в нашем коде. Учёт
  дешёвый (счётчики), удержание — только первый пакет потока.
- **Модули ядра** (`nft_socket`) — не везде; без них правила по программе
  недоступны, сказано прямо, запрет — отказ, а не «разрешить».
- **Сопоставление сокет → процесс** гоняется с короткоживущими процессами;
  непопавшее — «программа неизвестна», в правилах — как самое строгое.
- **Ложное чувство защиты:** разрешённый домен остаётся каналом. Окно говорит
  это прямо, рядом с «разрешить».
- **Приватность журнала** — §7.
