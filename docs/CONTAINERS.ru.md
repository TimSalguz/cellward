# Всё по умолчанию в контейнерах (M8) — дизайн

English: [CONTAINERS.md](CONTAINERS.md) · Связанные документы:
[LAUNCHERS.ru.md](LAUNCHERS.ru.md) (ярлыки), [CERTIFICATES.ru.md](CERTIFICATES.ru.md)
(доверие по контейнерам), [LEAK-MODEL.md](LEAK-MODEL.md), [GOTCHAS.md](GOTCHAS.md)

**Статус: предложение (2026-09-17).** Всё, что названо здесь «новым», ещё не
существует, если не помечено «сделано». Открытые вопросы в конце решает
владелец — до реализации.

## 1. Коротко

Сегодня запуск — это три независимых выбора на каждый клик: сеть (зона,
direct, offline), контейнер данных (основной, профиль-оверлей, одноразовый) и
песочница файловой системы (нет, своя, именованная, разовая). Дизайн сводит
три оси в одну сущность — **контейнер**:

> Контейнер — это именованная личность: дом, набор разрешений, набор доверенных
> сертификатов **и ровно одна сеть**. Экземпляр программы работает ровно в
> одном контейнере. Программы назначаются контейнерам, а не сетям.

Следствия, по важности:

1. **Личность нельзя разнести по сетям** ([LEAK-MODEL](LEAK-MODEL.md),
   «Открытые каналы» §4). Контейнер, привязанный к зоне `nl`, никогда не
   запускается в `direct`: пикер этого не предлагает, `vpn-zone run` отказывает.
2. **Ни один слой не теряется молча.** Любой запуск идёт одной дорогой — в зону,
   в `direct` или в `offline`. Баг с `direct`, исправленный в `fix/launch-path`
   (пикер терял контейнер, песочницу и ограничение композитора), — ровно тот
   класс, который так исключается по построению.
3. **Запуски мимо лаунчера попадают в нужный контейнер**: D-Bus-активация,
   автозапуск, бинды композитора, ссылки из других программ (§5).
4. **Ярлыки на каждую зону становятся не нужны**; их заменяет вид «по
   контейнерам» ([LAUNCHERS.ru.md](LAUNCHERS.ru.md) §4). Ничего не удаляется
   без согласия владельца.
5. **Всё декларативно** через опции модуля, плюс машиночитаемое состояние для
   nix_cm (§8, §9).

## 2. Что есть сегодня

| понятие | где живёт | что изолирует |
|---|---|---|
| зона | `~/.local/state/vpn-zones/<зона>/` + `vpn-zone@<зона>` | сеть (в app-ns только `lo` и туннель) |
| `direct` | нигде | ничего (сеть хоста) |
| `offline` | зона с маркером, создаётся по требованию | всё сетевое, включая резолверы хоста |
| контейнер-оверлей («профиль») | `~/.local/state/vpn-profiles/<имя>/` | XDG-каталоги (`.config`, `.local/share`, `.cache`, `.mozilla`, `.pki`) |
| одноразовый контейнер | `/tmp/vpn-profile-*` | то же, стирается за последним жильцом |
| именованная песочница | `~/.local/state/vpn-sandboxes/<имя>/{home,perms}` | весь дом, шина, runtime-каталог, seccomp, X11 |
| своя песочница программы | именованная песочница `app-<ключ>` | то же |
| разовая песочница | tmpfs | то же, стирается при выходе |
| ограничение композитора | `wl-sandbox`, включено по умолчанию | захват экрана, эмуляция ввода, фоновый буфер обмена |

Пикер помнит всё по программе: `.pinned`/`.last` (сеть) и
`.pinnedprofile`/`.lastprofile` (контейнер). Оси независимы — и именно поэтому
личность одной программы может переезжать между сетями.

## 3. Модель

### 3.1 Контейнер

```
контейнер = {
  имя          уникальное; селектор — тот, что уже пишет реестр
  дом          overlay | private | throwaway-overlay | throwaway-private
  сеть         <зона> | direct | offline | ask
  разрешения   файлы {downloads, documents, pictures, home}, x11,
               композитор {restricted | full}, (позже) имена шины, устройства
  доверие      дополнительные корневые сертификаты (CERTIFICATES.ru.md)
  программы    назначенные сюда (id ярлыков)
  источник     declared (Nix, только чтение) | local (CLI/GUI)
}
```

- **`дом`** один в один ложится на то, что есть: `overlay` — сегодняшний
  профиль, `private` — сегодняшняя именованная песочница (и своя `app-<ключ>`),
  одноразовые виды — сегодняшние `--tmp-profile` и `--fs-sandbox`. Каталоги
  данных остаются на местах: это часть контракта ([GOTCHAS](GOTCHAS.md) §5).
- **`сеть = ask`** — значение совместимости: сеть спрашивается при каждом
  запуске, как сейчас. Все существующие контейнеры мигрируют в `ask`. Контейнер,
  созданный новым GUI, привязывает сеть при создании.
- **Основной дом — не контейнер.** «Без контейнера» остаётся (системные
  утилиты, терминал с `sudo`), так и называется в интерфейсе и не может
  держать ни доверия, ни привязки.

### 3.2 Инварианты

- **I1. Одна сеть на контейнер.** Контейнер с привязанной сетью запускается
  только в неё. `vpn-zone run <другая> --profile <c>` — отказ с названным
  выходом («контейнер `c` привязан к сети `nl`; перепривязать: `vpn-zone
  container set c network <сеть>`»), а не молчаливый запуск.
- **I2. Один контейнер на экземпляр программы.** Уже верно по построению
  (реестр пишет селектор); проверка конфликта смотрит ещё и на бинарь (сделано
  в `fix/launch-path`).
- **I3. Все слои на любой дороге.** Сеть, дом, разрешения, доверие и
  ограничение композитора накладывает один путь кода (`vpn-zone run` →
  `entry_argv` → `profile-run`) — для зон, `direct` и `offline` одинаково.
- **I4. Незнакомое — без сети.** Программа без назначения по-прежнему получает
  «сети нет, пока её не дали» ([GOTCHAS](GOTCHAS.md) §2); с
  `defaults.container = own` — ещё и свой отдельный дом.
- **I5. Отказ вместо деградации.** Контейнер, привязанный к исчезнувшей зоне, в
  другой сети не стартует; слой доверия, который не удалось наложить,
  останавливает запуск ([CERTIFICATES.ru.md](CERTIFICATES.ru.md) §4).

### 3.3 Устройство одного запуска (порядок — это и есть спецификация)

```
[nsenter -U -n -m -t <зона>]  или  [unshare -U --map-current-user --keep-caps]   (direct)
  └─ unshare --mount --propagation private           всегда, когда что-то монтируется
      └─ vpn-zone-core profile-run --cwd <каталог> …
           1. дом: слоты оверлея (недостающие нижние каталоги — пустыми, 0700)
           2. герметичность runtime (§6, этап 4): tmpfs поверх /run/user/<uid>,
              сокеты возвращаются поимённо; tmpfs поверх /tmp/.X11-unix
           3. доверие: бинды бандла, базы NSS (CERTIFICATES.ru.md)
           4. chdir <каталог> → $HOME → /          (сделано: fix/launch-path)
           5. сброс ambient capabilities
           6. exec: wl-sandbox → fs-sandbox (bwrap) → программа
```

Всё монтируется в собственном mount namespace запуска, никогда — в namespace
зоны: два контейнера одной зоны не должны видеть слоёв и сертификатов друг
друга. bwrap биндит рекурсивно, поэтому песочница видит то, что смонтировали
шаги 1–3.

## 4. Выбор контейнера

Порядок для запуска программы `P`:

1. работающий экземпляр `P` (по id ярлыка): тот же контейнер — клик по
   запущенной программе означает «разверни окно» ([GOTCHAS](GOTCHAS.md) §11);
2. **декларативное** назначение (`programs.vpn-zones.apps.P.container`);
3. **локальное** закрепление (`.pinnedprofile`, а для контейнеров `ask` ещё
   `.pinned`);
4. вопрос.

Вопрос становится «сначала контейнер». Набросок меню (тексты условные,
окончательные пойдут через i18n):

```
Куда пустить «Firefox»?
  🔒 work — VPN nl · свой дом
  📁 personal — прямой · слой над домом
  ⚠ gov — VPN ru · свой дом · ДОПОЛНИТЕЛЬНЫЙ КОРНЕВОЙ СЕРТИФИКАТ
  ── разово ──
  Без сети, разовая песочница
  VPN nl, разовая песочница
  Без контейнера · прямой           (последним, без украшений)
  ── ──
  ➕ Новый контейнер…                (имя, вид дома, сеть — с привязкой)
  Всегда: …                         (закрепить программу за выбранным контейнером)
```

Сегодняшний диалог «сначала сеть» остаётся для контейнеров `ask` и для «без
контейнера» — ничего, на что человек полагается сейчас, не пропадает.

## 5. Запуски мимо лаунчера

Перехват — это **маршрутизация по умолчанию, а не граница безопасности**.
Процесс на хосте всегда может сделать `exec` пути в store напрямую; пользователь
хоста доверенный. Граница проходит в направлении «контейнер → наружу» (§6). В
таблице — все способы, которыми стартует программа, и что их направляет.

| путь | сегодня | предложение | этап |
|---|---|---|---|
| ярлык в лаунчере (меню, fuzzel/rofi, KRunner, noctalia) | теневой ярлык пикера в `~/.local/share/applications` | без изменений; вопрос «сначала контейнер» | 1 |
| записи, уже лежащие в пользовательском каталоге (игры Steam, `userapp-*` мессенджеров и браузеров, веб-приложения, Wine) | **не перехватываются**: чужие файлы не переписываются никогда | решение владельца, см. [LAUNCHERS.ru.md](LAUNCHERS.ru.md) §3.2 | 3 |
| записи-дети (`steam steam://rungameid/…`) | клонируются на каждую зону как отдельные программы | направляются в контейнер родителя | 1 |
| `xdg-open`, `gio open`, `kde-open`, «открыть с помощью» | находят `.desktop` → теневой ярлык | без изменений | — |
| D-Bus-активация (`DBusActivatable=true`, `gapplication launch`) | в тени `DBusActivatable=false`, но service-файл всё равно активирует мимо неё | теневые сессионные service-файлы в `$XDG_DATA_HOME/dbus-1/services/<id>.service` — только для перехваченных id, никогда для порталов и системных имён | 3 |
| автозапуск XDG (`~/.config/autostart`, systemd-xdg-autostart-generator) | стартует без контейнера | теневые записи в `~/.config/autostart` только для **назначенных** программ; никаких диалогов при входе; неназначенные перечисляет `doctor` | 3 |
| бинды композитора (`spawn` в niri, шорткаты KWin) | только если бинд сам зовёт `vpn-zone-pick` | `vpn-zone launch <id-ярлыка> [аргументы]` берёт `Exec` из самой записи (команда не дублируется в конфиге композитора); опция модуля отдаёт готовую командную строку | 3 |
| шелл | без контейнера | по желанию — PATH-шимы для назначенных программ (`~/.local/share/vpn-zones/shims`) с защитой от рекурсии; границей не являются | 3 |
| портал `OpenURI`/`OpenFile` из программы хоста | портал запускает запись обработчика → тень → пикер | без изменений | — |
| портал `OpenURI` из контейнера | то же, но происхождение теряется: ссылка из зоны может открыться в браузере в direct | брокер (§6.2) | 4 |
| ссылка или программа, открытая изнутри зоны (`vpn-zone run` в зоне) | делегируется через `systemd --user` (`launch.rs`, шаг 1) | та же дверь, но с охраной: брокер (§6.2) | 4 |
| `systemd-run --user`, `systemctl --user` изнутри зоны | доступны: процесс может запустить что угодно снаружи | герметичность runtime (§6.1) | 4 |
| `flatpak run`, `flatpak-spawn --host` | своя песочница flatpak; `--host` выходит через сессионную шину | у `private`-контейнеров шина уже отфильтрована; оверлеи получат это с §6.1 | 4 |
| программы, запущенные другими программами хоста | без контейнера | вне рамок (хост доверенный); `doctor` это называет | — |

### 5.1 Записи-дети

Запись — **ребёнок**, если её команда передаёт ссылку другой программе:
`Exec=steam steam://rungameid/<id>`. Признак: аргумент — URL, схему которого
другая запись объявляет как `x-scheme-handler/<схема>`, и обе записи запускают
одну программу. Ребёнок никогда не клонируется на зоны, а в режиме пикера
получает id родителя: где запустится игра, решает работающий клиент, игра — его
дочерний процесс, и сеть у неё клиентская ([GOTCHAS](GOTCHAS.md) §10). «Сеть
на игру» невозможна, пока запуском владеет клиент; честный интерфейс — «контейнер
Steam».

### 5.2 Команда запуска для биндов

`vpn-zone launch <id-ярлыка> [-- доп. аргументы]` находит запись по id в тех же
каталогах, что читает `sync`, берёт её `Exec` (коды полей — из доп. аргументов)
и становится пикером для неё. Бинд композитора называет программу один раз:

```kdl
Mod+B { spawn "vpn-zone" "launch" "firefox"; }
```

## 6. Граница наружу (этап 4)

Это пункты M3; контейнеры превращают их из глобальных переключателей в
умолчания контейнера.

### 6.1 Герметичность runtime

В mount namespace запуска: tmpfs поверх `/run/user/<uid>`, назад биндами —
только сокет Wayland (уже ограниченный), PipeWire, PulseAudio и сокет брокера;
tmpfs поверх `/tmp/.X11-unix` плюс `unset DISPLAY` ([LEAK-MODEL](LEAK-MODEL.md)
§7); по выбору tmpfs поверх `/run/dbus`. `private`-контейнеры всё это уже
получают через bwrap. Оверлеям это станет умолчанием, когда появится брокер, —
раньше это сломало бы открытие ссылок, которое сегодня держится на
делегировании.

### 6.2 Брокер

По сокету на контейнер, в его runtime-каталоге. Один глагол: «открой это» (URI,
файл, переданный дескриптором, или id ярлыка). На стороне хоста брокер знает
контейнер-источник, поэтому решение такое:

- программа назначена **тому же** контейнеру → запуск там же, без диалога;
- контейнер заперт → только тот же контейнер;
- иначе → пикер, и источник назван в вопросе («ссылка из `work` (VPN nl)»).

Изнутри контейнера к брокеру ведут три входа:

1. `xdg-open` и `$BROWSER` указывают на клиента брокера (бинд поверх
   store-пути `xdg-open` в mount namespace запуска);
2. делегирование в `launch.rs` (шаг 1) идёт в брокер, а не в `systemd-run`;
3. порталы: `private`-контейнеры перестают получать `OpenURI`/`OpenFile` через
   прокси шины (правила `--call` по интерфейсам порталов вместо сплошного
   `--talk=org.freedesktop.portal.*`). GTK, Qt и Firefox под `/.flatpak-info`
   зовут портал и на `xdg-open` не откатываются, поэтому до этого переключения
   нужен совместимый с порталом фронт для `OpenURI`. **Открытый вопрос
   исследования**: прототип в VM прежде любых обещаний.

## 7. Границы возможного без root

Что недоступно непривилегированному пользователю и почему. Каждый пункт — это
ограничение дизайна, а не задача.

- **Нет глобального перехвата `exec`.** События разрешений fanotify, хуки LSM и
  eBPF требуют `CAP_SYS_ADMIN`/`CAP_BPF` в исходном user namespace. seccomp
  user notification потребовал бы `NO_NEW_PRIVS` на всю сессию, что ломает все
  setuid-помощники (`sudo` и `newuidmap`, на котором стоят зоны), и всё равно не
  достаёт до детей `systemd --user`.
- **Нет сетевой политики по процессам на хосте.** cgroup BPF и `net_cls`
  требуют root. Сеть — это всегда namespace.
- **Работающий процесс нельзя перенести** в другую сеть или контейнер. `setns`
  действует на вызывающего; программа, стартовавшая снаружи, остаётся снаружи
  до перезапуска.
- **Файлы хоста не меняются — меняется только их вид.** Любое изменение `/etc`
  (бандлы, `nsswitch.conf`, политики браузеров) — это бинд или tmpfs в нашем
  mount namespace, а точка монтирования обязана уже существовать: внутри
  каталогов root ничего не создать.
- **Сессионную шину хоста нельзя отфильтровать для программ хоста** — только
  для контейнеров, через прокси.
- **Модули ядра** (`amneziawg`, `nf_tables`) из user namespace не грузятся, а
  `/etc/subuid` один раз требует администратора.
- **Программам со встроенным доверием или своим runtime** (Flatpak, pressure-vessel
  Steam, AppImage, `webpki-roots`) слой доверия снаружи не дать
  ([CERTIFICATES.ru.md](CERTIFICATES.ru.md) §2).

## 8. Декларативная конфигурация (опции модуля)

Для nix_cm, у которого правило «настройки программ — только опциями модулей»:
опции на входе, JSON на выходе (§9), разбирать наши файлы ему не нужно.

```nix
programs.vpn-zones = {
  enable = true;

  launcher.mode = "picker";              # picker | per-zone | both | off
  defaults = {
    network = "offline";                 # offline | direct | <зона>
    container = "ask";                   # ask | main | own | <контейнер>
  };
  compositorRestriction.enable = true;

  containers.work = {
    home = "private";                    # overlay | private
    network = "nl";                      # <зона> | direct | offline | "ask"
    apps = [ "firefox" "org.telegram.desktop" ];
    permissions = {
      filesystem = [ "downloads" ];      # downloads | documents | pictures | home
      x11 = false;
    };
    trust = {                            # CERTIFICATES.ru.md
      certificates = [ ./certs/some-root-ca.pem ];
      acknowledgeRisk = true;            # обязательно при непустом certificates
    };
  };

  interception = {
    dbusActivation = false;              # этап 3
    autostart = false;                   # этап 3
    userEntries = "leave";               # leave | take-over — LAUNCHERS.ru.md §3.2
  };
};
```

- Декларативные значения home-manager кладёт в `~/.config/vpn-zones/declared/`
  (ссылки в store, только чтение), и они **сильнее** локального состояния. CLI и
  GUI показывают их как «задано в Nix» и отказываются менять, а не падают на
  файле только для чтения.
- Сами зоны не декларируются: конфиг зоны — это приватный ключ, в Nix store ему
  не место никогда. Декларативный контейнер, названный на несуществующую зону, —
  отказ при запуске (I5), а не ошибка вычисления.
- Проверки при вычислении: непустой `trust.certificates` требует
  `acknowledgeRisk`; одна программа в `apps` двух контейнеров — ошибка;
  `permissions.filesystem` у дома `overlay` — предупреждение (не применяется).

## 9. Машиночитаемое состояние

`vpn-zone status --json` печатает всё; `vpn-zone container list --json` и
`vpn-zone container show <имя> --json` — подмножества той же схемы. В пределах
одной `version` изменения только добавляющие.

```json
{
  "version": 1,
  "defaults": { "network": "offline", "container": "ask",
                "launcher_mode": "picker", "compositor_restriction": true },
  "zones": [
    { "name": "nl", "backend": "amneziawg", "up": true, "locked": false,
      "handshake_age_s": 42 }
  ],
  "containers": [
    { "name": "work", "selector": "sb:work", "home": "private",
      "source": "declared", "network": "nl",
      "apps": ["firefox"],
      "permissions": { "filesystem": ["downloads"], "x11": false,
                       "compositor": "restricted" },
      "trust": { "extra": [ { "sha256": "…", "subject": "CN=…",
                              "not_after": "2030-01-01T00:00:00Z",
                              "source": "declared" } ] },
      "running": [ { "app": "firefox", "pid": 1234, "zone": "nl" } ] }
```

JSON пишется руками, как руками читается манифест (без `serde`): схема наша и
достаточно плоская. Единственный видимый потребителю контракт — этот документ;
каждый ключ закреплён тестом.

## 10. Куда теперь может уйти пакет или DNS-запрос мимо туннеля?

Вопрос для каждой части, как требуют правила проекта.

- **Привязка контейнера (I1).** Убирает путь, а не добавляет: личность больше
  нельзя кликом унести в другую сеть.
- **Контейнеры в `direct`** (сделано). Сетевого namespace нет по определению —
  программа пользуется сетью и резолверами хоста, и так и называется. Новый
  здесь только user namespace; прав над netns хоста он не даёт.
- **Mount namespace запуска.** Сеть не меняется; монтирования видны только
  этому запуску.
- **`vpn-zone launch`, PATH-шимы, тени автозапуска и D-Bus.** Только запускают
  пикер или `vpn-zone run`; ни нового сокета, ни нового маршрута.
- **Брокер.** Новый unix-сокет внутри контейнера — дверь с охраной: один глагол,
  и всё, что пересекает контейнеры, решает человек. Он заменяет неохраняемый
  путь через `systemd --user`, который строго шире.
- **Вывод JSON.** Называет зоны и контейнеры любому процессу пользователя.
  Внутри `private`-контейнера каталога состояния не видно вовсе; внутри
  оверлея весь дом и так читается ([LEAK-MODEL](LEAK-MODEL.md) §9) — нового
  ничего не раскрывается.
- **Слой доверия.** Не сетевой путь, а канал MITM; его собственный разбор —
  [CERTIFICATES.ru.md](CERTIFICATES.ru.md) §5.

## 11. Этапы и тесты

Каждый этап кончается VM-тестом, красным до и зелёным после
([LEAK-MODEL](LEAK-MODEL.md): «канал закрыт, когда есть тест, который его
размыкает»).

| этап | содержание | доказательство |
|---|---|---|
| 0 | фиксы пути запуска: `direct` не теряет слоёв, рабочий каталог, конфликт по id и бинарю (**сделано**, `fix/launch-path`); записи-дети | смоук: слой + netns хоста + свой userns в `direct`; `pwd` и файл, лежащий только в верхнем слое |
| 1 | сущность контейнера, привязка сети (I1), пикер «сначала контейнер», `vpn-zone container …`, `status --json`, опции модуля, миграция в `network = ask` | сценарные тесты CLI и пикера; VM: привязанный контейнер отказывает в другой сети; тест схемы JSON |
| 2 | слой доверия ([CERTIFICATES.ru.md](CERTIFICATES.ru.md)) | VM: синтетический CA доверен только в контейнере A |
| 3 | `vpn-zone launch`, тени D-Bus и автозапуска, дети в режиме пикера, записи пользовательского каталога (по решению владельца), PATH-шимы | VM: активация через `gdbus call`/`gapplication launch` попадает в контейнер |
| 4 | герметичность runtime, брокер, закрытие X11 | VM «злой хост»: `systemd --user`, считающий `StartTransientUnit`; портал, пишущий в лог, кто звал; HTTP-маячок |
